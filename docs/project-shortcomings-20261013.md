## 具体不足与建议

### 1. 自动研究在固定预算内形成有效交付的能力仍不稳定

2026-10-12 的固定任务复测包含 HotpotQA、QASPER 两项任务，首版与交付修订版各跑一次，共四次。每次研究主控和编码共享 360 秒、40 万已报告 token 的预算，结果为 **0/4 有效提交**：预算截止时仍缺少必需文件，未进入最终源码冻结后的独立评分。部分编码终结用量也缺失，成本只能记录已确认下界。

这说明该配置下，规划、实现与试验尚不能稳定收敛到可交付产物。项目已有有界 V4 闭环验收和历史成功案例；四次失败不能外推为全部任务都失败，但足以说明“流程可运行”和“在预算内稳定交付”之间仍有差距。

**建议：**先保证一个最小、可执行、可评分的基线产物；给最终文件检查和宿主评分预留预算；在截止前依据剩余资源减少非必要尝试。用同条件首次运行检验有效提交率，同时保留失败和用量缺失。

**同日发布前补充：**离线直接调用 `AutoResearch.implementation_evidence()` 复现了保守的恢复限制：同方案、同源码的诊断先超时、后成功时，历史失败仍参与全部通过判定，结果保持 `failed`；仅保留成功记录时为 `passed`。这会继续阻止 `goal_met`，并不会把失败冒充成功。当前需新方案或源码重新验证，尚未实现按确切诊断身份替代环境性失败的重试规则；后续修复应保留原始回执，并避免用其他诊断的通过掩盖真实失败。本轮仅记录该限制，未修改此行为。

依据：[最新固定任务复测](D:/project/researchagent/docs/resume/researchagent-20261009-evidence.md:137)、[已有有界闭环验收](D:/project/researchagent/docs/auto-research-goal-gap-20260929.md:24)。

### 2. 资料问答的稳定交付和完整性仍有提升空间

最新质量报告复用了完整配置的 20 道后续资料问答首次运行：**成功交付 17/20，严格全部达标 15/20**；正确回答交付率 16/20，完整性与引用充分性均为 15/20。仍有三次未交付，以及已交付但内容或引用未达标的任务。

该结果仅代表这组固定开发场景，不能视为所有研究任务的总体成功率。当前核验已有格式重试、期限约束和待核验草稿回退；这些保护避免误称核验通过，但仍会影响用户获得最终答案。

**建议：**按未交付、内容缺项、引用缺项、核验服务异常分别分析失败；优先恢复已有草稿和证据，减少重复检索；改动后在冻结面板上报告首次交付率、严格通过率与恢复成功率。

依据：[质量指标与失败分母](D:/project/researchagent/docs/research/llm-judge-metrics-20261013.md:7)、[核验重试](D:/project/researchagent/research_agent/verify.py:221)、[待核验草稿回退](D:/project/researchagent/research_agent/verify.py:608)。

### 3. 意图路由耗时较长，部分任务被错误分到聊天

近期 210 题路由测试中，标签复核后的准确率为 197/210。九道分类错误全部被分到 CHAT，包括三道联网查询、五道编码或实验请求、一道自动研究请求；另四道构思任务因模型超时失败。实验类召回为 **25/30（83.33%）**。

该轮单题路由耗时中位数 **14.07 秒，p95 为 45.44 秒**。网页使用后台排队，能够先接收消息，但用户仍需等待路由完成后才能进入相应流程。这是该轮模型与服务条件下的测量，不能当作当前所有请求的实时延迟。

**建议：**把路由延迟、分类错误和服务失败分开监测；优先针对已出现的错误补充新保留题，比较更短输出、更合适模型或有限的确定性入口。保留禁联网、禁执行及既有授权边界。

依据：[路由结果与时延](D:/project/researchagent/docs/research/intent-routing-and-judge-20261012.md:34)、[路由调用](D:/project/researchagent/research_agent/workbench.py:92)、[网页后台提交](D:/project/researchagent/web/app.js:469)。

### 6. Docker 构建可能带入本地研究与实验档案

### 7. 旧部署示例与当前本机使用边界不一致

旧文档仍使用 `-p 8000:8000`，新文档已改为 `-p 127.0.0.1:8000:8000`。容器内默认监听 `0.0.0.0`；若用户沿用旧命令且宿主网络允许外部访问，无登录的研究区、会话和资料接口就可能对可达主机开放。

本机能力检查会阻止公开监听时的原生实验执行，但不等同于基础数据接口的身份认证。同源检查也不能代替对直接 HTTP 客户端的认证。本次未检查当前服务是否对外暴露。

**建议：**统一旧示例的回环端口映射，或让旧部署章节明确指向当前说明；确有远程使用需求时再按已说明的反向代理认证方案部署。

### 8. 裁判输出可靠性与独立评测仍有缺口

### 9. 检索缓存命中前仍需全量读取并计算语料指纹

`sync()` 先读取完整语料，再序列化正文计算指纹，之后才判断缓存是否命中；命中后仍读取该范围的全部索引行。查询和跨会话检索还共享同一个 Retriever 锁。

因此，即使资料没有变化、只请求少量结果，准备成本仍随语料量增长；双路研究可能在检索阶段等待同一把锁。现有缓存主要省去重新切块、写索引等工作。此项是静态性能判断，未测得具体延迟或容量上限。

**建议：**维护语料变更版本，将索引同步与普通查询分开；查询优先读取命中项，逐步缩小锁范围，并用真实资料规模验证收益。

依据：[全量读取与缓存判断](D:/project/researchagent/research_agent/retrieval.py:288)、[检索锁](D:/project/researchagent/research_agent/retrieval.py:371)、[跨会话同步](D:/project/researchagent/research_agent/retrieval.py:501)。

### 10. 实时事件流之外仍持续全量拉取历史和任务

页面每轮刷新结束后等待 1.2 秒，再请求完整会话消息和研究区任务。对应消息接口不传历史条数限制，任务查询使用 `SELECT *` 且没有分页。

长对话和任务积累后，即使没有新内容，数据库查询、JSON 传输和前端处理也会重复发生。已有 DOM 差异更新和 SSE 游标减少了部分重绘与事件重复，但没有减少这两条接口的全量数据。本次未进行浏览器性能或大历史压测。

**建议：**消息按游标增量读取，任务列表分页并只返回展示所需字段；SSE 正常时降低全量轮询频率，详情按需加载。

依据：[全量刷新](D:/project/researchagent/web/app.js:303)、[轮询间隔](D:/project/researchagent/web/app.js:580)、[历史查询](D:/project/researchagent/research_agent/workbench_store.py:200)、[任务列表查询](D:/project/researchagent/research_agent/workbench_store.py:274)。

### 11. 核心执行职责集中，状态转换规则分散

当前 `auto_research.py` 约 1,406 行，`coding_tool.py` 1,268 行，`loop.py` 873 行，`workbench.py` 846 行。问题主要在职责集中：主循环同时管理工具、上下文、核验、预算与恢复；Workbench 直接装配 Agent 的多个可变属性，并直接更新任务 SQL；其他状态转换又位于 AutoResearch 和 Store。

**建议：**先集中任务状态转换和执行代次检查，明确 Agent 的配置入口；在相关功能实际改动时逐步提取独立职责，控制单次改动范围。

### 12. 最小安装包含重型检索依赖，依赖锁定入口不统一

**建议：**区分基础运行与可选向量检索的安装入口；明确各支持环境的依赖约束与验证方式，让文档、CI 和镜像使用一致的安装策略。

### 14. 记忆相关性筛选和转化为实际行动的能力仍不足

最新完整组在 16/20 道后续题加载了事实结论，17/20 道加载了过程经验，但只有 **1/20 道题**的工具调用直接使用记忆保存的原文位置。该统计严格按 `ref_id` 相等判断，只衡量直接定位，不能据此说其余记忆完全没有影响。

当前取用逻辑按检索结果顺序选择至多两条事实或经验，检查类型、状态、作用域、期限和来源可见性，但在该选择环节没有独立的查询相关性或预期效用门槛。向量候选有排名，不代表它足够值得进入当前问题的上下文；这是静态可见的筛选缺口，不能直接断言它造成了全部退化。

过程经验还存在“通用提醒很多、具体方法复用不足”的历史信号：10 月 12 日的 20 次完整方案运行中，19 次选中了相同的两条通用经验。当前提炼提示已要求具体动作、观察结果、章节或参数线索，不能再写成尚未实现具体经验提炼；不过最新加载数量仍不能证明经验已经稳定改变后续工具选择，也没有隔离出过程经验的单独收益。

**建议：**允许弱相关时返回空记忆，保留“为何适用于本题”的最小依据；需要原文定位时优先利用已有位置并核对原文。记录加载后的实际回读、动作变化和任务结果，用这些观察决定保留哪些经验，而不以保存条数或加载率作为效果指标。

依据：[事实与经验取用](D:/project/researchagent/research_agent/memory.py:174)、[最新直接复用统计](D:/project/researchagent/evals/reports/qasper-memory-nomemory-20261013/report.md:40)、[历史经验同质化](D:/project/researchagent/evals/reports/memory-learning-20261012/report.md:61)、[当前提炼提示](D:/project/researchagent/research_agent/experience.py:43)。

### 15. 当前记忆评测仍难区分表达变化、事实复用和持续学习

### 16. LongMemEval 拒答题处理仍不正确，历史指标需要复核

当前数据构建仅根据 `answer_session_ids` 是否能映射到会话判断 `unanswerable`，没有据拒答样本及原始消息中的 `has_answer` 标志调整答案证据。计分函数又只根据 `gold_context_ids` 是否非空及 `retrieval_eligible` 判断能否参与正例召回。

本次离线检查 50 道项目 LongMemEval 题，发现 **3 道 `_abs` 拒答题均被标为 `unanswerable=false`，保留了非空 gold，且会被作为可计分召回题**。其中开发集两题、保留集一题；三题的消息中均没有 `has_answer=true`。这会把不能支持答案的关联会话当作应召回的答案证据，混淆拒答表现与可回答题的检索质量。

历史 Recall@5 8.33%→33.47% 应继续作为原协议下的归档值保存，不能直接当作上述问题修正后的当前成绩。此前 37.47% 与 33.47% 的排名变化也需要结合实际版本和计分条件复核，不能在没有同条件重测时归因。

**建议：**统一可回答题的 gold 定义、拒答样本分类和指标分母；可回答题报告检索指标，拒答题单列应拒答时的表现；保留数据版本与旧结果，再用修正后的口径重测。

依据：[LongMemEval 构建逻辑](D:/project/researchagent/evals/build_mixed_benchmark.py:186)、[检索计分](D:/project/researchagent/evals/run_mixed_benchmark.py:137)、[项目任务数据](D:/project/researchagent/datasets/open/longmemeval/tasks.json)、[历史召回与排名变化](D:/project/researchagent/docs/resume/researchagent-20261009-evidence.md:25)。
