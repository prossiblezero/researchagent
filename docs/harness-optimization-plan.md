## 1. 目标和边界

让现有 search/read Agent 具备稳定的工具执行、可控的上下文、可靠的证据反馈和可复核的评测，为后续 Agent-RL 提供可信环境。

本仓库保留现有 SQLite、API 和 Web UI，但不在本方案中扩展研究区、资料工作台或复杂前端；这些由独立的 `D:\project\researchagent` 承担，见[工作台路线](deep-research-workbench-roadmap.md)。

继续采用 Python 显式编排。优先完善 `search`、`read`，正文抽取属于 read 内部能力，不为工具数量增加 Shell、浏览器或文件写入工具。新增工具必须有失败样例证明必要性，并补权限、预算和测试。

修改 Prompt、预算、反馈规则属于 Harness 优化。只有用交互奖励更新可训练策略参数，才称为 RL。长期记忆、Multi-Agent、前端和数据库都不是 Agent-RL 的必要前提。

## 2. 当前基线与待解决问题

| 模块 | 当前状态 | 需要解决的问题 |
|---|---|---|
| Loop | search/read、多轮调用、重复动作和预算检查 | 可纠正的错误直接终止；预算耗尽丢失总结机会 |
| read | HTTP 读取，有超时和字节上限 | 原始 HTML 噪声大；缺正文抽取、响应类型和网络目标的完整检查 |
| 上下文 | 追加消息、字符截断 | 缺输入 token 预算、结构化压缩和协议完整性保障 |
| Verifier | 词汇重叠、否定词规则、四类状态 | 不等于语义支持；结果未形成验证—补查闭环 |
| Experience | 任务内动作和模板反馈记录 | 缺具体证据缺口；不构成跨任务长期记忆 |
| Policy | 工具名、查询参数、URL 授权、输出审查 | 缺 SSRF、重定向检查；拒绝和恢复语义需分离 |
| Trace | JSONL 事件和截断内容 | 不足以重建训练所需完整 observation/action |
| 评测 | 7 条 fixture、15 条实时任务 | 样本小、缺独立测试和对照；引用统计口径存在问题 |

15 条实测的 8/15 仅是旧判分规则下的单次任务通过数。来源引用统计存在去重分子与未去重分母不一致；Evidence ID 存在不等于证据支持事实。旧报告保留用于追溯，不作为可信奖励或优化收益证明。

## 4. 分阶段实施

### H1：校准评测，冻结开发与测试边界

修改入口：`evals/run_live_eval.py`、评测任务文件及对应测试。

- 修复引用口径：统一按引用出现次数统计有效/无效引用，或统一按唯一 ID 统计；字段名明确口径。保留修复前原始报告，不覆盖历史。
- 分开记录引用 ID 有效率、答案正确率、Claim 证据支持率、任务通过率；找到了目标域名不代表答案受到该来源支持。
- 定义参考答案、可接受变体、证据要求、合理拒答条件；关键词仅作辅助诊断。
- 自编任务目标为 50 条开发集、100 条独立测试集；按主题和近重复问题划分，覆盖单跳、多跳、冲突、证据不足、API、时效性。安全攻击和正常安全知识问答单独分组。
- 开源数据记录许可证、原始 ID、来源链接、版本、抽样及改写方法。测试集不用于 Prompt 调优、记忆写入或训练。
- 报告记录代码/数据哈希、模型、日期、全部预算、运行次数、工具环境版本、判分器版本、失败原因、token、P50/P95 延迟。
- 每题独立运行 3 次，报告平均单次成功率、3 次至少一次成功率和 3 次全部成功率；明确样本和次数，不把不同配置下的历史运行拼成 Pass@3。

验收：人工构造重复引用、伪造引用、正确同义表述、关键词齐全但答案错误等样例，证明判分能区分这些情况；全部任务先审题再冻结。扩充后的效果指标必须真实执行后填写。

同步文档：`stage6.md`、`evaluation.md`、`live-evaluation.md`、`evaluation_research.md`。

### H2：先修网络边界和工具恢复，再跑大规模实时评测

修改入口：`policy.py`、`search.py`、`loop.py`、`models.py`、`contracts.py`。

- URL 在授权前规范化，只接受明确定义的等价形式；不能为了提高通过率放宽为任意同域 URL。
- 阻止 localhost、私网、回环、链路本地和保留地址；检查所有解析地址及每次重定向。连接实际目标必须受同一检查约束，不能仅预先解析一次后任由客户端再次解析产生 DNS rebinding 缺口。
- 保留现有超时与字节限制，补响应类型、重定向次数限制；HTML/plain text 之外明确返回不支持，不把 PDF 字节当正文。
- 区分硬安全拒绝与可纠正的参数错误。非法参数最多允许 2 次纠正，计入模型轮数；网络故障最多 1 次重试，计入请求次数和耗时。
- 预算耗尽后额外保留 1 次只允许 final 的总结调用。模型适配器不能仍强制允许工具；没有有效证据时继续合理拒答。
- 分别记录实际网络请求、工具尝试、拒绝次数和成功次数，避免重试隐藏成本。
- 前置/后置权限策略留在独立 policy 模块，Loop 只消费 allow/deny/recover 结果。网页标记为不可信数据只是提示约束，不能宣称已阻断所有注入。

验收：私网目标、重定向到内网、凭据 URL、未知工具均被阻断；正常参数错误可以纠正；预算后不再请求工具但可总结已有来源；全部请求有上限和终止原因。

同步文档：`stage1.md`（错误与 final 协议）、`stage2.md`（read）、`stage3.md`（预算与恢复）、`stage6.md`（权限与攻击测试）。

### H3：正文抽取和上下文预算

修改入口：`search.py`、`evidence.py`、`loop.py`、`models.py`；上下文逻辑独立为 `context.py`，不堆入 Loop。

- read 提取标题、段落和必要代码块，移除脚本、样式和导航噪声；保留 URL、读取时间、内容哈希和截断标记。
- Evidence 保存最多 200,000 字符的正文及独立摘要，超限显式标记；read 工具结果先回传有界正文，由下一次上下文构建决定是否需要摘录。
- 每次调用前按预算构建稳定规则、原问题、Claim 状态、Source/Evidence 映射、正文摘录和最近工具轮次；预算内且无待注入 Claim 时保留原始输入。
- 超预算时移除旧工具组，保留最近 2 组完整 tool call/result 配对；按问题相关性选取正文摘录，并避免跨消息重复同一 read 正文。不改写来源 ID，协议配对完整不代表正文永不缩短。
- read 摘录只有在完整序列化后确实更小时才采用，防止短正文加标记反而超预算；Trace 的 removed 按最终内容记录。
- 保护当前问题、未解决 Claim、冲突证据出处、最近错误和必要引用映射。保护内容仍超预算时明确失败，不能无限截断。
- 输入预算与输出预留分别计算。匹配 tokenizer 时记录 token 数；只能估算时记录估算方法和余量，不能伪称精确值。
- Trace 记录压缩前后大小、保留/移除对象、原因和耗时，不记录凭据。

验收：长网页和多轮轨迹触发压缩后请求协议仍合法；中英文问题、代码、来源 ID 和冲突关系保留；对同一组任务比较压缩率、正确率、成本，不能仅报告压缩百分比。

同步文档：`stage2.md`（正文与 Evidence）、`stage3.md`（上下文构建）、`stage5.md`（任务内摘要）、`stage6.md`（上下文对照实验）。

### H4：语义验证与反馈闭环

启动条件：第 5 节的跨仓库交接已完成，`researchagent` 已开始 V1；首轮交付时不启动本阶段。验证器增强应在工作台进入 V2 深度论文分析前完成对应验收。

修改入口：`verify.py`、`contracts.py`、`evidence.py`、`experience.py`、`loop.py`。

- 保留 lexical verifier 作为回归 baseline；增加结构化语义验证，输入只有 Claim 和指定 Evidence，输出 SUPPORTED/REFUTED/INSUFFICIENT/CONFLICTING、证据片段及理由。
- 将事实支持、来源权威性、时间适用性分开判断；权威来源本身不构成支持，模型自报 confidence 不当作校准概率。
- 先生成待验证 Claim，再验证；不足时最多 2 轮定向补查/修订，所有调用受总预算控制。验证异常不能默认判为支持。
- 反馈明确缺少哪个 Claim 的什么证据，并记录下一动作是否响应；不能仅使用“继续缩小证据缺口”的模板作为有效经验。
- 最终报告保留未解决问题与冲突，不通过删除困难 Claim 来提高支持率。

验收：用至少 100 组人工标注 Claim-Evidence 对校准，四类状态各至少 25 组，包含否定、数字、日期、实体错配和高词汇重叠反例；报告各类 precision/recall、混淆矩阵及分歧案例。LLM judge 结果需抽检，不视为绝对真值。

同步文档：`stage2.md`（Claim 构造）、`stage3.md`（补查）、`stage4.md`（验证器）、`stage5.md`（反馈作用）、`stage6.md`（验证器评测）。

### H5：跨任务策略记忆，可选且独立验收

启动条件：已解除第 5 节暂停，并有跨任务策略复用的实际需求。与工作台 V3 的需求衔接，不阻塞 V1/V2 的会话历史保存或本地论文检索；这些能力不等于长期策略记忆。

修改入口：`experience.py`、`storage.py`、上下文构建；需要时新增独立记忆模块。

- 只保存可复用检索策略，不把普通答案或未经证实的事实永久写入记忆。
- 条目包含适用任务类型、策略文本、来源 run、成功/失败计数、验证依据、更新时间、失效时间和启用状态。
- 写入候选至少经 3 个不同开发任务验证且无安全失败，再晋升；这只是初始工程门槛，不代表统计可靠性。
- 先按任务类型检索最多 3 条，使用 SQLite；不预先引入向量库。使用记录关联后续动作和结果，支持禁用、失效和删除。
- 评测前冻结记忆快照；测试集不写入策略库。比较无记忆和冻结记忆，控制其他设置一致。

验收：过期/禁用策略不召回；来源可追踪；失败能降低策略适用性；报告是否改善成功率、重复调用与成本。没有证据收益时不默认启用。

同步文档：`stage5.md`（任务内与长期记忆区别）、`stage6.md`（记忆消融与防泄漏）、`stage7.md`（存储迁移和清理）。长期记忆不作为 H6 的前置条件。

## 5. 实施顺序与量化验收

### 5.1 首轮核心加固与强制暂停点

```text
newagent：H1 校准评测 → H2 安全和恢复 → H3 正文与上下文
         → 首轮对照尝试与文档验收 → 交付同步材料 → 暂停
researchagent：同步已验收改动 → 回归与兼容性检查 → 开始 V1
newagent：确认恢复条件满足 → H4 验证闭环与增量对照
         → 按实际需求安排 H5、工具增强及可选 H6
```

“newagent 建立好”在本方案中指完成 H1–H3 的确定性验收，并完成代码、测试、运行工件与教学文档的同步。若真实 A–D 因环境阻断，可保留可审计的失败工件后进入暂停和交付，但该工件不算质量证据；成功、同版本的 A–D 配对结果仍是未完成项。只有代码跑通或只有离线 fixture 通过，不能宣称真实质量验收完成。

首轮执行下面定义的 A–D 对照；E 及记忆消融在对应功能实现后再运行。H1 的指标和数据边界先冻结，涉及网络的大规模实时运行放在 H2 网络边界修复后。记录全部实际结果，未证明收益时明确说明，不通过反复调整测试集追求高分。

首轮交付后将交付记录中的状态写为 `PAUSED_FOR_RESEARCHAGENT`。在恢复条件满足之前，不继续 H4/H5/H6、不扩充通用工具、不启动 Agent-RL，也不自行转去实现工作台 V1。暂停期间仅处理同步或回归暴露的首轮缺陷；发生修复时更新交付版本和验证记录。

### 5.3 恢复后续优化的条件

以下条件必须同时满足：

1. `researchagent` 已应用首轮 Harness 改动，并记录源版本与目标 commit 或文件哈希。
2. 目标仓库运行了对应回归测试及 CLI/API 基础联调，结果通过；发现的同步阻塞已解决。
3. V1 已实际开始开发，例如研究区或会话功能已有代码变更和开发记录。仅复制路线文档或表示“准备开始”不算开始；无需等 V1 功能全部交付。

用户明确告知上述交接条件已满足，或可核实的交付记录证明满足后，更新状态为 `READY_FOR_H4`。后续执行任务据此从 H4 继续，无需重新批准整份方案。没有这些信息时保持暂停，不能因等待时间已到就默认恢复，也不自动创建轮询或定时任务。

H4 完成后补 E 对照，并将通过验收的增量修复单独同步给工作台。H5 按需求独立开展；H6 留待独立训练需求明确后安排。新增通用工具继续按失败分析决策；工作台 V2 必需的 PDF 下载/解析、本地检索等产品能力由 `researchagent` 实现，不受通用工具扩充实验阻塞。

### 5.4 对照配置与指标口径

对照配置：A 一次检索后回答；B 当前 Agent 基线；C 修复执行问题；D 在 C 上加上下文治理；E 在 D 上加语义反馈。记忆另作 E 与 E+Memory 消融。

各配置固定任务、模型、最大工具/模型调用、token 上限；额外验证调用计入总成本。固定快照控制搜索波动，实时实验记录日期、重复次数和来源变化。不同预算实验分表报告。

主指标：人工/参考标准核验的任务成功率、答案正确率、Claim 支持率；同时报告正确拒答、误拒、攻击成功率、工程失败、工具次数、token、P50/P95 延迟和原始分子/分母。

按任务配对分析收益，给出置信区间并保留失败案例。无法确认提升时如实报告，不改判分条件追求高分；不承诺预设的通过率提升。所有新增指标必须有定义、反例测试和对应原始工件。

## 6. 实现与 stage 教学文档必须同步提交

仓库实际文件名是 `docs/stage1.md`～`docs/stage7.md`，不是 `stage_1.md`。沿用现有命名，不另建两套教学文件。

**每项优化只有在代码、测试、运行证据和对应 stage 文档全部更新后才算完成。不得只修改 README 或本方案就宣布阶段完成。**

每份受影响的 stage 文档保持以下组织：

1. **问题**：给出优化前真实失败输入和表现，说明旧实现为何不足。
2. **解决方案**：使用 Mermaid/清晰流程图，解释新增机制、边界和取舍。
3. **工作原理**：大白话配实际代码片段，解释输入、输出、状态和参数；代码必须与当前实现一致。
4. **试一下**：提供普通 `python` 运行命令、示例问题、成功与失败样例；逐个解释新增参数。只在环境配置处使用 `conda activate evidence-agent`，不使用 base。
5. **接下来的章节**：明确下一步和仍未实现的内容，不能把规划写成现状。

新增 Trace 事件必须展示脱敏后的真实 JSONL 内容，逐行解释事件、字段、单位和关联 ID。新增指标必须展示真实评测输出，解释分母、聚合方法及与正确性/安全性的区别。未运行的命令明确标为待验收。

涉及 API 配置时说明 `.env` 字段、读取优先级及真实/离线模式；不能展示密钥。数据库变更必须兼容已有数据，提供迁移与回退说明，不能删除数据库重建。

每阶段同时检查 `README.md`、`HANDOFF.md` 和对应评测文档是否过时；本方案中的状态只在完成验收后更新。

## 7. 工程检查和交付记录

当前已有的回归入口：

```powershell
conda activate evidence-agent

```

新增评测命令随实现落地到对应 stage 与 evaluation 文档；旧 `run_live_eval.py --limit` 不能替代新增数据集划分和多次重复实验。

每阶段交付记录包含：代码与数据版本、变更文件、测试命令和退出状态、成功/失败 Trace、真实报告路径、文档同步清单、风险及回退方式。安全与解析逻辑保留能在旧代码上失败的回归样例；不要用大量镜像实现的测试充数。

Agent-RL 不在本轮执行范围内。以后用户要求训练时，再基于已验收的 H1–H4 和所需 H6 能力单独制定训练方案，明确可训练模型、算力、训练数据规模、算法、奖励校准、冻结测试和训练前后对照。轨迹格式齐备本身不等于完成 Agent-RL。
