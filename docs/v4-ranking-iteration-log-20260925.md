# V4 排序退化修复：迭代记录

本轮目标是解释并修复 `64.92% → 43.89%` 的真实退化，完成新的量化验收。旧运行、旧数据划分和旧报告不覆盖；最终简要说明另存验收目录的 `report.md`。

## 1. 先复现退化

归档基线和候选的全部 60 题前十排名均被复现。候选在词法无命中时叠加来源密度和编号邻近奖励：一个邻段加 0.01，而 RRF 第 1–40 名分差约 0.00639，数量优势压过相关性。历史可回答题有 9 题召回下降、0 题上升；跨文档题前五名平均来源数从 2.4 降至 1.3。删除奖励项的诊断明确指出邻段项是主要退化来源。

流程也有问题：开发集只含 Docling 的 20 题；最后一次修改覆盖了较好首版；模型已报告开发退化，宿主仍对最后一版进行终验。完整证据见 `evals/reports/v4-first-cycle-20260923/regression-diagnosis-20260924`。

旧集上的一次有限融合权重探索未找到可用的召回提升；前两个临时诊断脚本有输入类型错误，修正后完成。它是已见数据诊断，不是新终验，也不用于从测试分数挑选新候选。

## 2. 调研与取舍

核对 DSPy / OpenEvolve 的最佳程序保留、Haystack 原文列表重排、Pyserini RRF/归一化融合及 MMR、ColBERT 的实现或官方论文出处。具体固定提交、已读范围与访问失败见 [调研记录](v4-ranking-research-20260925.md)。不引入新的 Agent 框架、图数据库或新编码器。

当中文问题没有词法命中时，单调改变 dense 权重不能修复其内部排序；本轮使用已有 Luna API 对固定候选原文判断支持度。模型只看到查询和原文，不见答案、gold、split；宿主验证编号和原文 span，记录请求、原始响应、用量、耗时及失败。此过程不是完整答案核验，span 匹配只证明原文来源。

## 4. 系统拥有候选选优

保留首候选和至多一次修订的代码快照。宿主仅在开发集复算，基线作为初始最佳；Recall@5 与 MRR 都不低于基线才可入选，再按 Recall、MRR 选择。锁定代码后才最终检验，负例代码与开发测量仍可查阅。无效源码、开发中断、无改善均有明确结果；中断不重放已经占用的开发测量次数。

## 5. 原文重排第一轮开发验证

目录 `data/v4-ranking-20260925/dev-content-pilot-r2`。24 次真实 Luna 请求，496,632 个已报告 token，计量 24/24；每题平均 14.65 秒，P95 49.34 秒，四路并行模型准备约 89.25 秒，BGE 准备另计。

18 道可回答开发题：Recall@5 `80.56% → 91.67%`，MRR `.6019 → .8056`；跨文档开发题 `58.33% → 91.67%`。原文候选池 Recall@40 为 100%。无答案开发题空结果 5/6，不能当完整问答拒答正确率。

发现 9/24 次退回基线，均因模型用多个 span 重复引用同一个原文片段。修复为：逐项验证编号/span，再按首次出现合并同片段排名，保留全部有效原文引用；未知编号、无效 span 和格式错误仍回退。第二轮使用新代码指纹、相同冻结开发题重新运行，并保留第一轮全部响应。开发期间添加的缓存并发防护只影响重复查询，同一批次问题文本互异；正式闭环前将再次冻结全部代码。
