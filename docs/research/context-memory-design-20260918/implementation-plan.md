# ResearchAgent 优化实施方案

日期：2026-09-18。检索方案已按用户澄清修订为 BGE-M3 + ChromaDB，SQLite 保留业务与原文数据；详见 [选型修订](retrieval-revision.md)。状态：设计方案，不是已完成的功能清单。调研依据见 [源码对照报告](research-report.md)。所有以下数值均为拟议初始策略或验收目标，不是已有实测收益。

## 目标与边界

让用户在同一研究区自然连续提问：需要论文证据时检索并回读，不依赖题名含某个关键词；长会话保留关键约束；新会话能按需找回历史决定和已存研究资料；可解释实际用了什么记忆、做了什么压缩、花了多少 token。

继续复用 `D:\project\researchagent` 的 Python、SQLite、ResearchAgent、资料库、Evidence/Claim、Policy、Trace、后台线程和前端。研究区默认隔离，下载仍使用已授权目录，评测下载根目录保持 `D:\paper`。不改 `D:\project\newagent`。

现有路线要求“普通 Python 显式流程”“单机优先”，早期阶段暂不引入向量数据库。上一版延续了无向量库取舍；本次用户明确建议 BGE + ChromaDB，故改为本地嵌入式 Chroma 组件，不增加独立常驻服务，也不迁移业务数据库。将原计划 V3 的部分记忆能力提前为研究连续性基础，是建议调整里程碑顺序；不把它标记为已经完成 V3。暂不加入创新方案执行、Coding Agent、多用户、分布式队列、知识图谱或自动多 Agent 编排。

**最小方案**：补全缓存用量记录、移动动态进度、取消标题预筛选、把现有索引接成工具。它即可改善可观测性与资料覆盖；仍不能可靠解决语义召回和跨会话失忆。

**推荐方案**：按下面四阶段演进；第二阶段先发布零新增依赖的工具化全文检索，再发布可选的本地向量召回。每个交付点都可独立运行，后续不实施也不会留下不可用的中间状态。

## 1. 运行结构与工具合同

结构中的循环仅存在于研究执行器；索引不反向调用模型生成答案，记忆整合不递归启动研究任务。

```text
用户消息 → 会话/任务队列 → 上下文构建 → 模型决定
                         ↑               │
                         │               ├─ 直接回答 → 引用检查 → 保存消息/报告
                         │               └─ 选择工具 → 范围/预算校验
                         │                                  │
                         └──── 工具结果 + 原文引用 ←──────────┘

工具：search/read（网络）     retrieve/read_evidence（资料、历史、记忆）
                     ↓                         ↓
                  现有获取器            SQLite + 原始文件 + Chroma HNSW

原始消息/工具事件 → 检查点             完成任务 → 有来源的记忆候选
                                              ↓
                                  校验/用户明确确认 → 跨会话记忆
```

保留 Router 的聊天快路径、操作识别和预算选择；RESEARCH 与 LOCAL_QA 进入同一证据循环，区别由任务允许的来源集合表达。LOCAL_QA 仍表示不做外部网页检索，不表示模型运行于本地。下载/导入继续是独立的有副作用任务，不能因为开放检索工具而自动扩大这些权限。

| 工具 | 输入 | 返回 | 程序必须检查 |
|---|---|---|---|
| search（保留） | query | 网页来源 ID、摘要、URL、时间 | 现有网络策略、请求预算 |
| read（保留） | url | 本次可读网页的 E 引用及受限正文 | 当前任务允许的已发现 URL |
| retrieve（新增） | query；corpus=documents/memory/history；可选 artifact_ids；top_k 默认 8、上限 12 | ref_id、来源类型、标题、位置、短摘录、版本、状态、召回路径 | 研究区由后端绑定，不接受模型提供 space_id；资料过滤只能缩小范围 |
| read_evidence（新增） | ref_id；可选相邻段数（0–2） | 原文段落/消息窗口、位置、内容哈希、可继续读取标记、E 引用 | ref_id 属于当前可见资料；内容未被修改/删除；一次读取有 token 上限 |

`retrieve` 不产生最终答案、不暗中调用另一个问答 Agent。查询的语义展开由主模型完成，允许选择不同 query 再取证。低分结果明确标为弱候选，零命中不等于证明不存在。

新共享循环统一使用运行内 E 编号，E 指向稳定原始标识（资料/版本/原 L chunk/位置，或历史消息 ID）。旧 S/E/L 报告不重编号；来源展示和精确摘录校验继续复用现有逻辑。历史 Agent 报告、用户回忆、摘要和论文原文在 source_type 中区分。

需要一起修改 ModelDecision、模型解析、工具参数验证、Loop 分发和离线模型：保留经过验证的完整 arguments，不能继续只提取 query/url。近期仍一次执行一个工具；服务端返回多个调用时明确拒绝或要求修正，不能静默丢掉除第一个以外的调用。

所有检索/阅读请求计入任务动作预算；网络请求独立计数。重复动作可返回已有结果，但一次重复不立即强制总结；连续两次没有新证据的重复动作才进入停止判断，给出剩余缺口。缓存键包括资料版本与检索配置；网页搜索近期只做 run 内复用，避免跨任务旧结果冒充最新状态。

## 2. RAG：全文召回、混合检索和按需深读

### 2A：可以立即独立交付的基础检索

复用 `artifacts`、`document_chunks` 和文件权限检查，新增同研究区的 FTS5 索引。先搜索完整可见语料，再按用户明确指定的文献/年份/类型过滤；取消“只看最近 100 份标题再挑最多 8 份”的检索前置门槛。标题是加分信号，不是必含词约束。

索引内容包括标题、章节与正文；英文使用规范化词项，中文额外写入二元分词索引文本，原文不修改。DOI、arXiv ID、论文别名与连字符差异单独规范化。FTS 查询通过绑定参数与词项转义生成，不直接执行模型生成的 FTS 表达式。少于两字的查询不做全库模糊扫描，要求模型补充实体或从已指定文件内读取。

每次词法召回最多 40 个候选，最终默认返回 8 个短摘录；资料问答没有指定单篇时避免同一文献挤满结果，每篇最多 3 条，若相关文献不足则按相关性补足而非丢弃唯一证据。返回总文本上限为可用上下文预算 B 的 15%，同时不超过估计 2,000 tokens。模型需要更多内容时调用 read_evidence。

搜索模式是“找到位置 → 回读父段/相邻段 → 比较证据”。不需要为每个短段单独生成 LLM 摘要，也不默认给每条检索结果加昂贵重排调用。

### 2B：BGE-M3 + ChromaDB 的正式语义召回

采用 `BAAI/bge-m3`，revision 固定为 `5617a9f61b028005a4858fdac845db406aefb181`。输出 1,024 维稠密向量，支持多语言及最长 8,192 token 输入。本阶段只使用 dense 分支；稀疏分支和 ColBERT 不因模型支持就全部接入。用官方支持的 Sentence Transformers 接口，归一化向量；不沿用 E5 的 query:/passage: 前缀，BGE-M3 官方说明不要求为查询添加指令。

按标题/章节/段落切分，初始子段上限 512 个 BGE-M3 tokenizer token、重叠 64，引用绑定原始父 chunk、页码和字符位置。8,192 是模型输入能力，不表示每个片段都应填到上限；表格或跨段问题通过 read_evidence 回读父段。

Chroma 使用本地 PersistentClient，目录为项目 `data/chroma/`，单个后端进程拥有该目录；用 HNSW 与 cosine 空间检索。保持该锁定版本的 HNSW 默认参数作为初始配置，在固定样本上比较 ef_search=100/200 的 recall/latency；先选 100，只有后者改善召回且满足 P95 门槛才提高。向量模型由应用明确加载，文档与查询都传入显式 embeddings，避免 Chroma 默认 embedding 模型和 BGE 混用。

Chroma 向量 top 40 与 SQLite FTS5/BM25 top 40 做 RRF 融合，k=60，按内容去重及文献多样性取 top 8。精确论文 ID 匹配保留。Chroma 的 where_document 内容过滤不能当成 BM25 排名；本方案的词法排名继续由 SQLite FTS5 提供。reranker 暂不作为必须依赖，先在上述流程上测质量。

SQLite 继续作为原始资料、会话、记忆、权限与引用的权威存储；Chroma 是可重建的派生索引。集合按 embedding 模型/revision/维度区分，服务端为每次查询加入当前 space_id 及语料类型过滤；模型不能选择别的研究区。Chroma 命中只作为候选，后端回 SQLite 核对可见性、当前内容哈希与索引状态后才返回原文。

双存储没有共同事务，需显式处理同步：在 SQLite 保存索引状态 pending/indexed/failed、chunk 版本和任务 ID；后台对确定性 ID（space + chunk + 内容哈希 + 模型 revision）做幂等 upsert；成功后标记 indexed。删除/权限撤销先在 SQLite 生效，未清掉的向量也不得通过回表验证。崩溃后重试 pending 工作；模型升级建立新集合，完成后切换索引版本，旧索引保留到回滚窗口结束。检索结果数量不足时在同一次有界检索内补候选，不能让失效旧命中挤掉全部有效证据。

直接依赖拟固定 `chromadb==1.5.9`、`sentence-transformers==6.0.1`、`numpy==2.5.3`，放入 `requirements-retrieval.txt`；安装发布前在独立 Python 3.12 环境锁定传递依赖并做兼容回归。本次只核对官方发布要求，未安装。模型仍位于 `data/models/`，不改变论文下载目录 `D:\paper`。不增加 API key 或云账户。

默认不在首次聊天时隐式下载模型。完成依赖/模型准备并建立索引后启用语义检索；未安装、索引未完成或模型失败时继续 B1，并明确显示 lexical_only 与覆盖率，不冒充完整混合检索。BGE-M3 比原 E5-small 更重，CPU 速度、内存和 GPU 加速收益都需要本机实测，不能用 HNSW 查询快代替端到端延迟。

B2 放行条件仍为：保留集 Recall@10 比 B1 至少提高 5 个百分点，精确实体查询不退步，热检索 P95 不超过 2 秒（10,000 子段，含查询 embedding、HNSW、FTS 和融合），来源/删除/隔离检查全部通过。增加 10,000/100,000 子段的 HNSW 对精确余弦 top-k 召回、构建耗时、冷启动、RSS 与磁盘指标。10 万个 1,024 维 float32 原始向量约 410 MB，HNSW 和元数据还有额外开销。以上是目标与容量估算，尚无本机实测。

上一版 E5-small + NumPy 全量扫描保留为轻量/精确检索对照，不再是正式主路径。若 BGE-M3 的本机性能不满足门槛，保留 B1 可用状态并报告具体瓶颈，不隐式切换 embedding 模型或混合不同维度索引。

## 3. 上下文：稳定前缀、原始记录、结构化检查点

### 预算与组成

继续使用实际代码中的 quick/standard/deep 工具上限 8/16/24，应用上下文上限 16,384/32,768/65,536；原输出预留 2,048、安全余量 256。应用预算不代表模型或中转站真实窗口。若服务明确提供更低窗口，取较低值；未知时标记未知，不从别名推断。

可用输入预算 B = 上下文上限 − 输出预留 − 安全余量，计算必须包含系统提示、工具 schema、消息、记忆和工具内容。优先使用可取得的 tokenizer；否则保留估计方法名称，并用成功请求的实际 prompt_tokens 校准下一请求估计。不要把累计账单 token 当成当前上下文大小。

上下文排列为：固定 system 规则与固定工具 schema → 有版本的小型研究区/记忆快照 → 当前压缩检查点 → 按时序追加的近期消息、工具调用和结果。动态进度随新事件追加，不改写第一条 system；最终预算限制仍由程序执行。外部材料和检索记忆保留数据身份，不升级为系统指令。

同一批材料连续提问时可以固定材料块；检索结果发生变化的普通问答，不每轮把新材料插入历史之前。正常过程中保持前缀追加；用户纠正、遗忘、权限变化、模型切换后的预算不足可主动重建。

### 压缩策略

- 新工具结果先按 token 预算分页/限长；完整原文已经归档，返回原文引用和继续读取入口。
- 输入超过 B 的 80% 时，在工具调用/结果已经成对落盘的边界触发压缩；目标为 B 的 60%。不能在等待工具返回时压缩半个调用。
- 先处理已经完成、较旧的大工具结果。投影一经发给模型就固定，直至下一次正式压缩；原始事件不改写。
- 仍超目标时，用当前选定模型生成一次结构化检查点；不用未经用户选择的模型隐式降级。
- 保护最新完整用户要求、仍有效的明确约束、未结束工具调用、任务身份，以及近期完整工具对。至少保留最近两对；近期尾部目标预算为 B 的 25%，单个超大结果通过原文引用缩短。
- 核心记忆快照上限 min(1,024, B×5%)；检查点上限 min(2,048, B×15%)。若受保护内容本身放不下，明确指出过长内容并要求拆分/另开会话，不静默截掉最新问题。
- 检查点的固定字段：目标、明确约束及消息来源、已完成事项、待办/阻塞、关键发现及 E 引用、冲突/未核验项、已检索方向与失败原因、下一步、原始事件覆盖范围。
- 程序检查字段、引用存在性、任务一致性、受保护待办及原文指针。检查有效并不等于语义摘要绝对正确，因此另外做语义保留评测。最多一次纠正；失败保留旧检查点，不以失败摘要覆盖会话。确定性裁剪作为明确标记的降级，不冒充语义压缩成功。

触发阈值与释放目标形成间隔，避免压完一轮立刻再压。连续两次压缩没有释放有效空间就停止自动压缩，返回需要缩小单个输入的状态。摘要成本、纠正成本及耗时全部单独入账。

暂不使用原生 Responses compaction 作为必须能力：当前 Chat Completions 中转接口未验证支持；后续即使使用，也保留应用层可读检查点用于切模型、审计与恢复。

## 4. 会话内记忆、跨会话记忆与来源规则

| 类型 | 内容与生命周期 | 加入模型的方式 |
|---|---|---|
| 原始历史 | 用户/助手消息、工具事件；按会话持久保存 | 最近尾部或 retrieve(corpus=history) |
| 工作状态 | 本会话目标、约束、计划、证据缺口 | 当前状态与检查点；新会话不继承未完成任务 |
| 核心偏好 | 用户明确表达的偏好与研究区说明 | 会话起始小快照；用户纠正立即生效 |
| 研究记忆 | 带来源、时间、状态的研究结论与决定 | 按需 retrieve(corpus=memory)，需要时回读原文 |
| 资料库 | 原论文、代码文件、技术文档与历史报告 | retrieve(documents) + read_evidence；保留来源类型 |

### 写入与整合

普通研究结论先作为候选记录，来源至少是具体原文 E 引用、用户原消息或可验证的操作结果。现有 verify.py 的 SUPPORTED 仅词项启发式，不作为长期事实晋升条件，也不改写旧评测结果。

用户明确说“记住/以后按……”时保存偏好或决定并展示写入结果，不再问一次相同确认。用户没有表达的偏好不能由模型猜测写入。网页/PDF 中的命令、研究区外的资料以及仅从旧摘要推出来的新结论，不能成为用户偏好或行为约束。

候选研究事实在完成来源/精确位置检查和针对该结论的语义支持检查后，可标为 evidence_checked；它表示证据已核对，不表示世界事实永远正确。未经这一步的候选仍可检索，但必须明确标识，不能作为已核实依据。影响重大或冲突未解的条目保持 candidate/conflicting，用户可确认或拒绝。核心自动快照优先放确认偏好与当前约束，研究事实一般按需检索。

同主题重复记录做合并，保留每一来源；新结论通过 supersedes 指向旧版本。事实有 observed_at/valid_from/valid_until 与来源哈希，材料变更或删除后变为 stale。用户当前消息优先于旧记忆；两份论文结论冲突时同时保留，而不是按最近时间盲目覆盖。

提取在研究完成或产生会话检查点之后排队，利用已有结构化 findings，最多一次小型补充提取请求；闲聊没有新信息时零写入、零总结请求。整合由原后台线程的低优先级维护任务执行，交互任务优先；单机事务防止重复合并，不增加独立调度服务。

### 读取、修正与遗忘

默认只读当前研究区记忆，跨会话共享不等于跨研究区共享。没有全局自动用户画像；以后若需要全局偏好，再由用户明确提升其范围。

新会话选择已确认偏好与最多 8 条相关研究区摘要组成快照，固定到 memory revision；大批历史走工具读取。会话期间普通后台新增记忆只在下一自然边界使用，避免每轮改写前缀；显式纠正、遗忘和权限变化立即使相关快照失效，缓存收益让位于正确性。

前端提供查看来源、修改、拒绝候选、忘记条目。忘记会标记 tombstone，排除索引，令包含它的派生记忆/检查点失效，并登记被禁用的来源提取记录，防止后台从同一旧记录重新生成。普通“忘记这条记忆”不等于删除原始聊天；界面分别提供会话删除与记忆遗忘，明确其范围。删除原始资料后不能继续用失效索引回答其内容。

保留现有 research_space → conversation → message/job 关系，不另造同义 session 实体。

- 新建：共享研究区资料与允许的长期记忆，生成新的工作状态。
- 继续：恢复最近有效检查点及未压缩事件；切模型只影响下一轮，实际模型随每条请求保存。
- 分支：从已完成的用户轮次边界建立子 conversation，记录 parent_conversation_id / fork_event_seq；不复制整个资料库，也不自动合并子分支结论。
- 归档：隐藏于活动列表，可搜索恢复；不删除资料或长期记忆。
- 取消：使当前 job 的运行版本失效，禁止迟到回调写最终回答；取消不撤销已完成下载。
- 重启恢复：保留 interrupted 状态，用户点“继续”后载入已提交检查点和工具结果；已完成的只读工具不重复执行。无法确认完成的下载先检查目标文件/哈希，再给出恢复或重试，不自动重复副作用。

同一会话同一时刻只允许一个运行轮次；后续消息按顺序排队。新消息保存后可以立即显示，但它的路由与历史构建在轮到它运行时进行。为消息增加 turn_seq 和 parent_message_id/所属 job，按逻辑轮次组织上下文，避免“后发问题先入库、前一轮回答后入库”造成指代读不到上一轮答案。

前端至少增加：会话重命名/归档、从完成轮次分支、继续中断任务、查看本轮使用的记忆、查看压缩次数与范围。木屋主题、字号、复制、Enter 发送、模型下拉框和报告页继续复用；Trace 增加检索、压缩与记忆事件。

## 9. 故障、规模与回滚

**最脆弱的前提**：BGE-M3 能在此机器上提供有价值的语义召回和可接受的端到端延迟。若前提不成立，B2 不放行，B1 继续运行；不会为了维持方案再强制部署远程服务。现有框架只需支持两条已知检索分支，不提前造通用插件系统。

- 模型/网关不可用：保留原历史与最近有效检查点；不清空会话，不把失败当“没有相关资料”。
- 检索索引落后：按资料哈希排除陈旧命中，显示覆盖率，增量重建；不能拿旧向量绑定新原文。
- 语料增长 10 倍：先按研究区过滤、增量嵌入与 HNSW 检索，测索引内存和过滤后召回；只有业务并发、统一事务/关联查询确有需求时才迁移 PostgreSQL + pgvector。大模型和索引工作不能阻塞取消检查。
- 长期摘要漂移：保留原始事件范围与证据指针，支持重建；当前用户纠正优先，不能递归把摘要内容当新一手证据。
- 迁移：停止写入期间做 SQLite backup；在同一迁移事务新增结构并记录版本；旧资料只建立派生索引，不原地改写原文。先在数据库副本跑迁移和恢复测试，再更新本机实例。
- 回滚：每阶段独立提交。回退应用版本时保留新增表和列，旧路径仍可读取原消息/报告；停用 B2 不删原文或记忆。不要为了回退版本覆盖掉新产生的用户数据。只有迁移失败且尚无新写入时才恢复备份。
