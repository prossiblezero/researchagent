# 意图路由、融合策略与 LLM-as-a-Judge（2026-10-12）

本次为现有七类意图路由建立可重复评测，并将实测结果用于简历。分类调用真实 `route_intent`，只判断下一步；不执行搜索、下载、编码或自动研究。分类正确不能替代完整研究任务成功率。

## 数据与评测口径

[冻结数据](../../datasets/intent_routing/v1.json)共 252 题，开发集 42 题、测试集 210 题，初始各类均衡；后续复核纠正 4 个标签，当前测试集 CHAT 34、AUTO_RESEARCH 26，其余各 30。正式测试的 24 题选自 [MASSIVE v1.1](https://huggingface.co/datasets/AmazonScience/massive) 的中英文原始 test split，186 题为项目场景；来源映射与许可证见[数据说明](../../datasets/intent_routing/README.md)。MASSIVE 原任务是 60 类，本次仅取能映射到聊天/联网信息查询的三个原类别，不能称为官方 MASSIVE 准确率。

自建题覆盖本地文件、历史记忆、下载、创新构思、单次实验、自动研究，并加入多轮指代、否定约束、状态询问、引文中的指令等边界。实施代理依据既有产品定义标注，测试前由另一审查代理核对标签与规则，补全六条尚未运行题的缺失主题或配置；保留修改记录和旧哈希。不是独立人工盲标，也不是生产流量随机采样；不同题可能共享措辞和任务模式。

计分使用 exact accuracy、固定七类 macro-F1、逐类召回和混淆矩阵。所有 API/结构/预算失败均留在完整分母中；另报 Auto Research 在其他六类题上的误触发率。判分是预先标注的离散标签比较，不使用 LLM 裁判。每次运行冻结数据、源码、模型、预算；首次请求、格式修复、失败和未知用量分别保留，禁止重跑取最好成绩。

调用模型为已配置的 `api.sudocode.chat / gpt-5.6-luna`，沿用服务配置的 temperature（未显式设置），额外设置 4096 输出 token、每题 60 秒、4 个并发。开发集上限 420 秒/80 次请求/30 万已报告 token，测试集 1200 秒/280 次请求/150 万已报告 token。程序还对在途请求和未知用量预留额度。分类只接收生产路由提示、公开/合成会话与合成研究区信息，标签、理由、样本 ID 不入模型请求。没有加载真实聊天或本地研究资料。

开发诊断轮因 Windows 拒绝重复替换汇总文件中断；全部逐题记录离线复算后为 10 题返回、11 次物理请求、9 题分类正确，另 32 题未完成，在完整 42 题分母下为 9/42。该失败轮原样保留，不能用 9/10 冒充整组开发集准确率。评测器改为逐题保存、结束后一次汇总，新增回归检查在旧版复现故障、修复后通过。未重跑已测开发题。正式测试使用修复后的隔离快照；生产路由提示和函数没有为本次测试修改。

## “三路融合＋投票”是什么

这个名称没有统一实现。常见三路是规则/关键词、向量相似度、大模型分类；也可能是三个不同模型，或同一模型使用三个提示。每路输出类别及置信度，再做多数票、加权评分或按优先级仲裁。向量余弦相似度与模型自报置信度不是同一种概率，不能未经校准直接相加；同源模型或相似提示的错误也可能相关。

例如用户说“只调研自动实验方法，暂不运行”，关键词和近邻样本都可能偏向自动研究，理解否定约束的大模型才给出 RESEARCH。多数票可能把明确的限制覆盖掉。增加三路还会增加示例库维护、阈值校准、调用成本及冲突处理。

查到的成熟实现并不都使用三路多数票：

- [Semantic Router HybridRouter](https://github.com/aurelio-labs/semantic-router/blob/main/semantic_router/routers/hybrid.py)融合稠密与稀疏表示，代码中按 `alpha` 和 `1-alpha` 缩放；这是两种检索信号融合。
- [Rasa policy ensemble](https://github.com/RasaHQ/rasa/blob/main/rasa/core/policies/ensemble.py)在适用预测之间结合置信度和策略优先级选出结果；这是对话动作策略仲裁，不是本项目七类意图的直接基线。

本项目当前采用结合上下文的单 LLM 路由，外加 JSON 结构校验、格式修复时保持已识别意图，以及后续执行权限/预算约束。先保留此结构。只有在新采样的真实场景中发现稳定错误或明显时延、成本瓶颈，才值得评估“可确定规则或高置信近邻先处理，其余交给 LLM”的级联。任何优化都应同题同模型预算比较准确率、macro-F1、误触发率和成本；明确禁联网/禁执行约束应作为不可被投票覆盖的边界。此次没有实测融合方案，因此不能声称单路胜过融合。

## 项目已经有哪些 LLM 裁判

**运行时核验**在 [research_agent/verify.py](../../research_agent/verify.py)：模型逐项判断需求是否回答、拒答是否有依据、答案段落是否被其绑定的已读证据支持，驱动补读与修订。这是 LLM-as-a-Judge 的实际用途，不是只存在于说明文档中。

**离线语义评分**在 [evals/run_agent_benchmark.py](../../evals/run_agent_benchmark.py)：输入冻结 criteria、参考证据、实际证据和候选答案，输出每项要求是否满足、是否有据、是否存在实质矛盾。只有全部要求满足、有据且无矛盾才通过。

**混合评测裁判**在 [evals/run_mixed_benchmark.py](../../evals/run_mixed_benchmark.py)：输出 `correct`、`citation_sufficient`、`refused`、`unsupported_additions` 四个布尔标记；最终通过还要求产品成功交付。这四个字段不是四项 0–10 分，`refused=true` 也不自动意味着答得好。

[裁判校准脚本](../../evals/calibrate_agent_judge.py)已有正确答案、角色倒置、虚构数字、没有实际证据、裁判提示注入等对照样本。部分评测可使用不同的执行模型和裁判模型，部分链路复用同一模型；不得统一写成独立裁判或把裁判输出当真实标签。当前任务核实其实现，没有重新运行裁判校准或声称新的裁判准确率。

## 四个维度应该怎么选

没有通用规定必须四维。若看到的是 [Ragas 常用指标](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)，常见四项为：

|指标|回答的问题|
|---|---|
|Context precision|检索到的证据里，有多少有用，排序是否靠前？|
|Context recall|回答所需的证据是否找全？|
|Faithfulness|回答中的断言是否被给出的证据支持？|
|Response relevancy|回答是否回应了用户问题？|

这些指标不都等于回答正确性，也不能用高均分抵消关键事实错误。若为 ResearchAgent 做产品质量面板，更直接的四维是**事实正确、需求完整、证据/引用支撑、约束遵守**：前三项复用现有语义核验，工具权限、联网范围、预算及格式则尽可能从程序与轨迹直接判断。此次补充的是已有能力的准确说明，没有新增四维数字打分系统，也不为意图分类额外调用 Judge。
