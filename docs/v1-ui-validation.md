# V1 体验修订验收 · 2026-09-16

## 问题

用户反馈 arXiv 检索不明显、字体小、Trace 只能下载、目录必须手填。实际用户任务 da321030d18e44049735b152efb865b1 已返回 arXiv 来源，但 6 次调用全用于综合搜索、没有 read，来源混入二手网页。问题在于缺少明确检索范围及阅读安排。

## 解决方案

- 发送研究时可选择 web/arxiv，后台存储并在重试中保留；旧数据自动默认 web。Tavily 使用 include_domains，适配层再次限定 arxiv.org 及子域的 abs/html/pdf 论文路径。不调用原生 arXiv API。
- 引导前 1–2 次搜索后读取已返回的原始 URL；不改动 Harness 的 URL 授权边界，不允许自行猜测 HTML 地址。
- 重排页面、增大正文字号到 17–18px，安全渲染基础 Markdown，新增结果、来源与证据、实时过程三个页签。
- events API 按序号追加，约 1.2 秒刷新；每批最多 200 条，未完成末行留待下次读取；保留展开详情、滚动位置和 Trace 下载。
- Windows 本机、回环绑定且同源访问时，独立 tkinter 进程打开系统文件夹窗口。取消不修改原目录；窗口并发受限、超时退出。远程/容器保留手填路径。没有增加第三方依赖。
- 显示可读的连接失败说明并自动重连；失败写入不自动重发。

- 独立测试服务浏览器验证：新建研究区、提交任务、运行中已显示 12 条事件，完成后自动增至 21 条；展开的 #7 详情在后续轮询仍展开。来源页显示 1 条页面证据和 1 条搜索摘要。390px 窄屏无水平溢出、正文 17px；默认桌面布局已查看。

- 增加原始 URL 约束后，同一问题的最终真实流程 4/4：2 次 search、3 次 read、10 个来源、10 条摘要与 3 条页面证据，任务 completed。报告：`evals/reports/v1-ui-arxiv-live-final-20260916.json`。来源哈希随报告保存。

## 边界

真实流程通过只说明检索、阅读、报告链路可用，不代表回答正确率。该次模型报告中自述“1 次检索”与 Trace 的 2 次不一致，实际调用数以 Trace 为准；未做论文结论质量评分。模型仍可能选错来源、只阅读摘要或得到截断正文。

系统文件夹接口及子进程成功/取消/超时分支使用模拟返回做了回归，tkinter 已确认可导入；本轮未人工操作原生文件夹弹窗，因此不宣称完成原生窗口端到端视觉验收。浏览器按钮与可用状态已检查。

V1 只保存资料目录，PDF 下载/解析、本地资料问答仍待 V2。目录选择不是浏览器下载文件的“另存为”设置。服务默认仍是单用户本机应用。

## 试一下

运行 `python server.py` 后打开 `http://127.0.0.1:8000`。输入框旁选择「arXiv 论文」，发送一个具体研究问题。任务生成后切换「实时过程」，可以直接查看搜索词、读取地址、成功/失败和事件详情。研究区设置中选择保存文件夹；后续 V2 使用该配置下载资料。

验收在隔离临时副本和独立数据库执行；更新前备份目标文件及 SQLite，不修改 `.env` 和原有研究记录。旧的 docs/v1-files.sha256 和历史验收报告保持不变，新版文件清单为 docs/v1-ui-files.sha256。
