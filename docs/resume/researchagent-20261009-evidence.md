## 七类意图识别与 LLM-as-a-Judge（2026-10-12）

第1条新增的意图识别指标来自 **MASSIVE 公开子集＋项目自建场景**，共252题：42题开发、210题正式测试。正式测试含24道原文不变的MASSIVE中英文题、186道项目场景题，调用现有生产路由及 `gpt-5.6-luna`；标签、理由与样本ID不进入请求。七类覆盖聊天、联网调研、本地资料问答、下载、创新构思、单次编码/实验和自动研究。自建题包含多轮指代、否定约束、状态询问及引用中的指令，不是生产流量随机样本，也不是独立人类盲标。

原始冻结标签下，首次完整测试为 **193/210，准确率91.90%，macro-F1 93.09%**。正式测试启动后，由另一审查代理在不读预测的条件下复核88道相关场景，发现4道题没有研究主题，按既有产品规则应先走CHAT澄清，结果归档后将其gold从AUTO_RESEARCH纠正为CHAT。保留全部首次回答后为 **197/210，准确率93.81%，macro-F1 94.98%**；4次模型服务超时仍计错，AUTO_RESEARCH在其余类别中误触发为 **0/184**。没有删题、修改题目输入或重跑；这次分数变化来自标签纠正，不能写成路由优化收益。

简历正文明确注明“经标签复核”，采用93.81%；原始91.90%及全部失败一并保留。该成绩属于项目适配的七类评测，不能称为MASSIVE官方60类准确率、完整Auto Research成功率或优于Codex/三路融合的结果。公开子集单独为21/24（87.50%）。运行协议、类别分布、四题修正理由和局限见[意图识别与裁判报告](../research/intent-routing-and-judge-20261012.md)，两套指标、逐题预测/失败及哈希见[可复算证据](../research/intent-routing-results-20261012.json)。252题意图集与正文原有320条研究任务池分别统计。

2026-10-12时，第5条补充的是项目已有的LLM-as-a-Judge：运行时检查需求覆盖与逐段引用支持；离线评测按冻结的参考证据和criteria判断正确性、有据性及实质矛盾，再结合程序检查决定通过。不是本轮新增四项0–10分的打分器，部分链路复用执行模型，该日尚未重新测裁判准确率；2026-10-13已在上节链接的报告中补充80条校准结果。意图分类本身直接比较离散标签，不调用LLM裁判。

## 记忆与经验学习（2026-10-12）

第3条将已有会话记录、研究区共享记忆、全局偏好、历史混合检索和上下文压缩，与本轮新增的过程经验提炼作为一套完整记忆设计。受 [JitRL](https://arxiv.org/html/2601.18510v4) 的外部经验驱动决策思路启发，在模型参数冻结时，从真实工具动作、核验反馈和任务结果提炼至多一条“适用场景＋建议做法”，后续任务检索至多两条参考经验。存储、来源追溯、编辑与忘记均复用现有功能；具体机制是提示层的经验归纳与复用，未实现论文的动作优势估计或 logit 重加权。

简历比较起点仍是原始关键词记忆方案的 **Recall@5 8.3%**。本次使用原 LongMemEval 25道保留题与配对来源种子，按实际返回top-5、2,000 token预览预算及会话去重口径复测：关键词 **8.33%**，当前历史混合检索 **33.47%**，正文取一位小数写 **8.3%→33.5%**。此前保存的37.47%是历史结果；本次11题返回会话顺序或成员变化，原因尚未确认。该检查没有过程经验条目，衡量历史检索，不单独证明新经验机制的收益。

新增后续任务评测复用10条真实公开任务轨迹和12份资料，生成10条过程经验；20道新问题分为历史信息复用、跨资料比较、实验方法和证据不足四类。当前同一Agent分别使用原始关键词历史配置和完整记忆配置，每题各执行一次，共40次任务；文档检索、模型和预算相同，测试期间冻结记忆。它是同源后续问题对照，未单独测试用户偏好，也不是跨领域泛化评测。首次答案、独立评分请求、实施代理的原文复核和成本见[评测报告](../../evals/reports/memory-learning-20261012/report.md)。

40次首次运行完成后，严格任务完成率为 **13/20（65%）→15/20（75%）**，逐题3个改善、1个退化。严格完成要求产品成功交付、答案正确完整、引用充分且无实质性错误添加。平均作答token **105,945→108,027（增加2.0%）**，平均耗时 **170.6→157.7秒（减少7.5%）**；另有10条过程经验提炼的28,974 token，以及既有事实提取/支持检查和外部评分成本。这组结果不能表述为节省token。第13题基线内容被外部裁判判为正确，但内部核验失败；第18题基线遗漏冻结要点中的配对后分类，完整方案补齐。第7题则由基线通过退化为完整方案上下文超预算，详细依据见[逐题结果](../../evals/reports/memory-learning-20261012/pairs.md)。

面试可解释为：“受JitRL通过外部经验影响后续决策的思路启发，我在原有记忆模块里加了从任务成败轨迹归纳方法、在新任务开始时检索复用的闭环。改变的是外部记忆和任务上下文，模型权重保持不变。与原始关键词记忆配置相比，历史召回从8.3%到33.5%；另设的20道同源后续任务中，完整方案完成率从65%到75%，但token略增。这是整套记忆方案的结果，没有把全部提升归因于新增的过程经验。”

## 正文采用的 API＋Prompt 对照：超长资料与 SciFact 子集（2026-10-10）

正文所称“自建超长资料问答任务集”是组合公开题与项目题形成的14题评测集，包含2题QASPER、6题SciFact及6题项目公开资料问答。其中，公开数据集 **SciFact的6题问答子集**以 **5,183篇摘要**为语料库，Agent完成 **6/6（100%）**，同条件单次API＋Prompt完成 **2/6（33.3%）**，相差 **66.7个百分点**。这6题均包含在前述14题中，不能相加为20题；沿用同一冻结评分标准，衡量检索、作答与引用的整体任务完成情况，不是官方完整SciFact测试集成绩，也不同于第2条的Recall@5检索评测及第4条的开发集分类实验。逐题记录见子集复算与任务清单（本地档案：`research-notes/direct-api-24-20261010/value-evidence.json`）。

同一固定24题、同一 `deepseek-v4-1-flash` 模型、temperature=0及严格评分标准，直接提供原始文本和固定Prompt，不使用检索、工具或答案修订。流式整组实测任务完成 **12/24（50.0%）**；优化版Agent复用同题历史成绩 **18/24（75.0%）**。

## Multi-Agent 协作范式（对应当前精简稿第4条）

项目采用 **Supervisor–Worker（主控—Worker）的层级式编排**，子 Agent 通过工具接口接受委派，即 **Agent-as-a-Tool**。两个独立研究分支采用 **fan-out/fan-in**：由主控分发，等两路进入终态后汇合，再决定下一步。整体有中心主控，不是 Agent 之间互相派单、协商推进的点对点网络。

| 角色 | 职责与实现 |
| --- | --- |
| 主控 Agent | `AutoResearch` 根据当前观察拆分问题、选择顺序或并行研究、汇总证据，并决定保存方案、委派编码、执行实验、继续迭代或结束。 |
| 研究子 Agent | 每次 `research_parallel` 委派两个独立子问题，最多两个研究执行槽；每个子 Agent 有自己的模型消息、工具循环、证据与检查点。有前后依赖的问题用 `research` 顺序执行。 |
| 编码 Agent | 外部 Codex 经 `CodingTool` 接收已委派的方案并实现代码，作为主控的工具参与；研究目标与下一步仍由主控决定。 |
| 宿主程序 | Python 程序执行实验命令、采集并校验指标，管理预算、权限、队列和恢复；它是执行与约束层，不另算一个 LLM Agent。 |

选择这种范式，是因为两路调研最终需要汇总成同一个实验方案，研究目标、预算和结束条件也需要统一协调。子 Agent 可以独立使用工具查证，主控通过结构化结果接回报告、错误和证据，再决定补充调研还是进入实验。这样能明确每项任务的责任、失败状态与证据出处。

并行子研究可以共用数据库 `conversation_id`，但模型上下文通过固定历史边界隔离，兄弟任务新生成的回答不会混入另一方初始历史。汇合时用 `(job_id, evidence_id)` 区分两份报告里的同名证据。两个子任务均进入终态才唤醒主控，并分别保留成功或失败信息；编码与实验仍沿用串行执行器。

面试可用 30 秒说明：“我采用有主控的分层 Multi-Agent。主控负责研究目标和下一步决策，把两个独立问题交给研究子 Agent，各自检索、阅读和核验后返回结果；主控汇总成方案，再工具化委派编码 Agent。实验由宿主程序实际执行并回传指标，主控据此继续迭代或结束。”

实现入口见 [AutoResearch](../../research_agent/auto_research.py) 的 `dispatch()`、`parallel_result()`、`tick()` 及 [CodingTool](../../research_agent/coding_tool.py)；上下文隔离、任务汇合与恢复见[并行研究教程](../tutorial/09-parallel-research.md)。下方 SciFact 数字衡量生成候选的方法效果；并行专项验证了真实执行重叠，但现有对照未体现整体提速，两者分别解释。

## Agentic RAG 的实现与表述范围

正文第2条的 Agentic RAG 指由模型控制的多轮检索与阅读：模型依据问题和已有证据，选择调用 `retrieve` 检索、调用 `read_evidence` 分页读取原文，或生成答案；核验反馈返回执行循环，在剩余预算内可补充检索并修订答案。上一轮读到的论文标题、作者或引用可以成为下一轮的查询线索，从而支持多跳检索与跨文档整合。实现见[Agent 执行循环](../../research_agent/loop.py)、[检索与原文阅读工具](../../research_agent/retrieval.py)及[工作台本地问答入口](../../research_agent/workbench.py)。

Agentic RAG 的依据是模型根据中间结果决定后续动作。FTS5/BM25、BGE-M3 和 RRF 提供底层混合检索；同条 SciFact Recall@5、MRR@5 只衡量这层的检索效果，不能单独证明多跳问答准确率。可选的独立查询规划策略默认关闭，见[策略配置](../../research_agent/strategies.py)；正文“自主调整查询”指 Agent 在工具调用轮次间生成后续查询，不声称默认启用了独立规划器。

正文采用 **任务完成率80%**，对应十题同题复测（本地档案：`research-notes/author-relations-20261010/report.md`）的8/10严格通过，要求成功交付且最终答案完整、正确、引用充分。10/10成功交付作为工程诊断指标保留在附件，不在简历正文单列。原 Agentic RAG 基线（本地档案：`research-notes/author-network-20261010/report.md`）的8/10交付、6/10严格通过保留为前后对照，分母和评测条件在此说明。自建任务集以预先导入的五篇团队论文和一篇其他团队干扰论文为语料，共10题，覆盖作者与机构消歧、方法比较、引用跳转、共同引用、无答案控制和多篇关系归纳。该成绩衡量整组跨文档任务，不是纯多跳检索召回率。

| 指标 | 原 Agentic RAG 基线 | 增加作者／引用检索后的复测 |
| --- | --- | --- |
| 严格任务完成 | 6/10（60%） | 8/10（80%） |
| 产品成功交付 | 8/10（80%） | 10/10（100%） |

严格完成要求成功交付、满足冻结的事实检查项、引用充分且无实质性无据添加。优化后新增通过q07（共同引用）和q09（上传与发表年份），原已通过的六题没有退步；q04、q10都成功交付，但仍有归纳漏项或引用缺陷，故严格通过为8/10。见优化后统计（本地档案：`research-notes/author-relations-20261010/metrics.json`）、逐题复核（本地档案：`research-notes/author-relations-20261010/review.json`）及冻结题目（本地档案：`research-notes/author-relations-20261010/panel.json`）。保留原轮6/10记录与简历采用优化后8/10并不冲突。

成功交付衡量任务是否完成产品交付流程，不证明所需证据已经全部检索到、保留在最终输入中或被正确利用。严格完成衡量最终答案的完整性、正确性和引用支持，属于整个 Agentic RAG 与所用模型共同决定的端到端质量。即便调用外部模型API，项目仍可改进问题拆解、证据组织、上下文保留、漏项检查与局部修订。q04已读到选锚和双学习依据却漏答，q10存在方法细节遗漏及引用错位；这些记录不足以把剩余失败全部归因于API模型能力上限。

前后两轮使用相同十道题、六篇原文、`deepseek-v4-1-flash`、temperature=0、standard档、16次工具预算、20轮、32768上下文和600秒核心执行期限；每题隔离资料状态，强制走本地问答入口，禁用联网与历史召回，每轮每题只运行一次。题目和原文由实施代理准备并复核，未经过独立专家评阅；这是已知开发题集的同题复测。运行条件见优化后冻结协议（本地档案：`research-notes/author-relations-20261010/protocol.json`）。该组成绩与24题端到端指标分别记录，没有 GraphRAG 对照组。

q06沿 DLPMAC 的参考文献找到题目未直接给出标题的 CAPIMAC，并阅读原文解释方法；q07实际调用新增的共同引用查询，找到两篇论文共同引用的 CAPIMAC 后回读原文。q09没有调用新关系工具，其通过体现该轮交付改善，不能把全部20个百分点的变化都归因于关系索引。五篇整体归纳仍有细节遗漏，不声称任意作者网络或全库全局归纳均已稳定通过。

另行测试的联网作者拓展不计入上述10道本地题的分母。人工补充三份原文后，同一五篇论文开发任务已完成四篇候选核验（4/4），最终源码再次核验全部答案段落通过，见最终交付实测（本地档案：`research-notes/manual-paper-final-20261010/report.md`）。4/4是一题内部候选覆盖；失败、服务断线与续跑记录均保留，不用于上调十题的8/10严格通过成绩。

现有实现可以明确表述为 Agentic RAG，补充了作者消歧及显式引用关系检索。当前结果支持保留这条路线；是否需要社区摘要等完整 GraphRAG 能力，仍应由更大语料的独立对照评测判断。

## 面试表述

“我做了一个面向论文调研的 Agent 工作台，问答采用 Agentic RAG：模型根据每轮拿到的证据决定继续查什么、读哪篇原文，再整合跨文档结论，并根据核验反馈补证据或修订答案。比如读到一篇论文的参考文献后，可以继续查找并阅读被引用论文。在自建的团队论文多跳检索与关系问答任务集上，任务完成率为80%；这组评测有10题，按答案完整性、正确性和引用支持评判，另两题仍有内容或引用缺项。底层用关键词和向量混合检索，复杂任务还能拆给多个 Agent 并行处理，需要验证方案时调用编码工具开展对比实验。在另一组预先按输入长度划分的14题超长资料问答子集中，同模型与单次16K上下文预算下，任务完成率为85.7%，较原文按序截取的单次API＋Prompt基线35.7%提高50个百分点，其中SciFact的6题问答子集以5,183篇摘要为语料，任务完成率为100%，同条件API＋Prompt为33.3%。这些结果体现从大资料库定位和组织证据的价值；检索和记忆另有专项评测。”
