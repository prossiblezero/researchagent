# ResearchAgent 相比单次 API＋Prompt 的价值与面试表述

现有实验支持资料库检索与证据组织的价值。简历围绕相对原文直接输入的收益，以及Agent在跨文档问题中继续补证据的具体作用展开；完整方法对照保留在[评测报告](../research/rag-comparison-20261011.md)。

## 可以直接引用的结果

|任务范围|单次 API＋Prompt（流式）|项目 Agent|Agent相对单次API的差值|
|---|---:|---:|---:|
|全部固定24题|12/24（50.0%）|18/24（75.0%）|+25.0个百分点|
|原始资料超过单次上下文的14题|5/14（35.7%）|12/14（85.7%）|**+50.0个百分点**|
|SciFact：从5,183篇摘要库回答6题|2/6（33.3%）|6/6（100%）|+66.7个百分点|
|项目文档：从174段公开资料回答6题|1/6（16.7%）|4/6（66.7%）|+50.0个百分点|

相对单次API的主要论据是14题超长资料子集：按输入长度分组的规则已经在运行前冻结，包含全部该类成功与失败；逐题为Agent多完成7题、API多完成0题。它不是事后只挑7道Agent成功题。四行存在包含关系，不能相加成新的样本数。

比较条件必须保留：同一模型配置与单次16K上下文预算，直接API按原语料顺序装入能容纳的完整段落前缀；Agent能够多轮访问完整资料库。Agent使用10-09历史实测，直接API在10-10运行，传输方式和时段不同，总调用量与token不相等。这是特定基线下的系统级效果对照，不是模型纯推理能力或统计显著性的结论。

数据来自完整报告（本地档案：`research-notes/direct-api-24-20261010/report.md`）、逐题指标（本地档案：`research-notes/direct-api-24-20261010/metrics.json`）、本次独立复算及任务清单（本地档案：`research-notes/direct-api-24-20261010/value-evidence.json`）。原简历的25%→75%仍指旧版Agent到优化版Agent，两个比较口径分别保留。

2026-10-11补充核验恢复：两条旧失败恢复后累计完成记录为20/24（83.3%），其中超长资料组13/14。上述表格与简历仍引用首次运行成绩，累计记录不冒充最终版本整组实测。

## 面试时可以直接说

> 我做的是让用户直接围绕整个论文或技术资料库提问的研究系统。模型负责理解和生成，我实现了混合检索、按需原文阅读、跨文档证据组织和引用核验，系统根据中间结果继续补证据。在固定单次16K上下文预算的评测中，相比按语料顺序直接输入原文的单次API＋Prompt，24题任务完成率从50%提高到75%；其中14道资料超过单次上下文的任务，从35.7%提高到85.7%；这14题中的SciFact六题使用5,183篇摘要库，任务完成率从33.3%提高到100%。这组结果体现了系统把大资料库转化为可回答证据的能力。

已写入简历第1条：

> **任务执行与恢复：** 构建 Agent 执行框架，支持任务路由、工具调用校验、超时控制和断点续跑，记录执行过程并核验、修订答案。在 **自建超长资料问答任务集**中，使用相同模型与单次 **16K 上下文预算**，任务完成率达 **85.7%**，比只用 **API＋Prompt** （**35.7%**）提高 **50 个百分点**。其中，在 **SciFact 问答子集（6 题、5,183 篇摘要）**上，任务完成率为 **100%**，高于同条件 API＋Prompt 的 **33.3%**。

该表述已同步到[当前简历正文](researchagent-20261009.md)第1条，展示14题超长资料子集的总体结果，并补充其中公开数据集SciFact的6题结果；这6题的语料库含5,183篇摘要，样本存在包含关系。传输条件和历史结果复用放在证据附件。全部24题的API基线50%、旧版Agent基线25%及团队论文80%分别属于不同口径。

## 能展开讲的具体案例

**案例一：从大摘要库找到反证。** 问题是“高CRP是否降低COPD急性加重风险”。直接API的固定前缀没有相关摘要，回答NEI。Agent在5,183篇摘要库中检索CRP、COPD等条件，定位到本地文档D4131，读取完整摘要，回答CONTRADICT，并保留“三项炎症标志物同时升高，非CRP单项效应”的限定。原始记录为一次检索和一次原文阅读，事实方向与引用均通过原标准。实际答案（本地档案：`research-notes/subset-e2e-20261009/runs/scifact-516/after/answer.md`）

这里可展示的工作是查询执行、库内定位、从片段进入原文以及把结论绑定到证据。研究结论本身由公开论文提供，不能说是项目发现了新的医学结论。

**案例二：把跨文档问题执行到底。** 问题同时问LangGraph MemorySaver重启后是否保留检查点，以及LlamaIndex生成过多查询如何限制。Agent先发出两条针对性检索，分别阅读持久化指南和QueryFusionRetriever源码。首次核验发现额外的“资料未提供其他限制机制”断言缺少支持，随后按offset补读源码并修订，再通过核验。最终答清RAM检查点随进程丢失，以及`queries[: self.num_queries - 1]`截断和原始查询的数量关系。直接API在缺少这两份相关原文时拒答。实际答案（本地档案：`research-notes/subset-e2e-20261009/runs/project-independent-ind-cross-02/after/answer.md`）

完整请求链可核对：两条检索（本地档案：`research-notes/subset-e2e-20261009/runs/project-independent-ind-cross-02/after/requests/001.json`）、两份原文阅读（本地档案：`research-notes/subset-e2e-20261009/runs/project-independent-ind-cross-02/after/requests/002.json`）、首次核验（本地档案：`research-notes/subset-e2e-20261009/runs/project-independent-ind-cross-02/after/requests/005.json`）、补读源码（本地档案：`research-notes/subset-e2e-20261009/runs/project-independent-ind-cross-02/after/requests/006.json`）、再次核验（本地档案：`research-notes/subset-e2e-20261009/runs/project-independent-ind-cross-02/after/requests/009.json`）。这体现已执行的工具编排和补证据能力；单个案例不能估计该环节的独立增益。

**案例三：论文关系与身份核对。** 在赵亮团队论文场景中，系统通过共同引用查询，找出DLPMAC与KNNDA都引用CAPIMAC，回读两侧参考文献和CAPIMAC首页署名，确认Liang Zhao是第二作者兼通讯作者；没有因他不是第一作者漏掉这篇，也没有把共同引用直接推断成相互继承。自建十题最终完成8/10；人工补充受限原文后的另一完整任务核验了4/4篇候选的作者、版本和关系。十题报告（本地档案：`research-notes/author-relations-20261010/report.md`）、共同引用答案（本地档案：`research-notes/author-relations-20261010/runs/q07/answer.md`）、四篇候选验收（本地档案：`research-notes/manual-paper-final-20261010/report.md`）

团队论文指标属于另一任务集，未做同题纯API对照，适合展示领域功能和实现深度，不用它宣称优于API的量化幅度；人工下载保留为明确的参与步骤。

## 面试追问的回答

**“我把正确材料贴给模型，也能答出来。”**

可以，这与实验一致。项目面向的是用户还没有找齐材料的资料库问答：定位原文、筛选段落、补充上下文及保持证据来源由系统执行。14道超长资料题的50个百分点差距对应这一过程的收益。没有量化人工节省时间，所以不编造“节省多少小时”。

**“为什么把检索做成Agent可选择的工具？”**

资料问答往往需要在读到结果后才知道下一步缺什么。真实的IPA标注案例需要补读实体标签；MemorySaver＋LlamaIndex案例需要分别查两份资料，并在核验反馈后继续读取代码。当前实现先区分聊天、本地问答和联网调研，再由Agent选择查询、原文阅读和结束时机。面试时可以用这两条实际执行链说明设计；调用节省率尚未测量。

**“完整资料子集为什么API是7/10，Agent是6/10？”**

首次运行差的一题两边内容都正确，Agent因内部核验服务异常未正式交付而失败。该题恢复后，累计完整资料组为7/10；这不是整组重跑。这个结果说明额外流程有可靠性成本，也说明项目价值应围绕需要获取资料的任务来评估。完整资料子集的结果继续公开保留。

**“有没有代价？”**

有。流式API生成平均9.17秒；历史Agent平均151.61秒，包含检索、阅读、内部核验及产品后处理。生成/任务侧已知token分别为191,198与1,828,540，Agent另有3次请求用量未知。这是额外执行成本换取更多任务完成，当前结果不支持更省token或所有问题都更快的主张。
