## 1. 让已读到的证据稳定进入答案

完成记录：[限定真实验收](../evals/reports/harness-strategies-20260921/verification-recovery-20260923/report.md)。256项后端、27项前端、V1/V2及全部离线Stage通过。列表与紧邻纯引用说明合并核验，引用尾注后关闭列表续接，不跨无关说明段借用引用。恢复复用已有检查点和已通过段落；跳过会话重新摘要及已保存动作前的不必要上下文压缩，界面提供「继续核验草稿」。原模型核验超时仍可能发生，本轮不以延长超时掩盖异常。

验收限定在最终核验阶段：三条旧修订稿、同原文、同模型前后配对；错误事实/错源/摘要负例；一次注入中断后的真实恢复。恢复发现原稿补充段引用不足，1次局部修订后通过，主段落逐字保留且复用；没有重新检索或重新生成整份回答。旧16次端到端成绩不重算，跨文档漏读问题继续保留。本步已经达到限定收尾目的，不再扩测才启动V4。下面保留当时的排期依据。

直接依据：最终16次中，ReAct 列表和干扰题存在事实正确但列表段引用绑定失败；精确参数基线草稿正确但核验超时。当前 `research_agent/verify.py` 的 `answer_blocks` 按空行分块，仅对表格后的来源说明合并引用范围；生成/修复行为还涉及 `loop.py` 与 `models.py`。

最小方向：先将上述原始失败固化为本地回放用例，明确列表、表格及尾随来源说明的引用作用域；让生成和修复遵守同一分块合同，仅在范围明确时关联证据。优先修正文档结构与绑定契约，不凭相邻位置给任意事实补引用。复用已有已通过段落缓存与检查点，让超时后的操作可以只续跑未完成核验，并显示进度和剩余缺口。

交付标准：原失败及相邻反例通过回归；错误引用、没有原文的事实仍会失败；已通过段落不重复核验。之后进行一轮固定真实对照，报告完整任务通过、有效引用、漏答、修复次数、核验超时恢复率和延迟。事实任务失败与服务异常分别计数，总失败仍全部保留。

主要风险：扩大引用作用域会把无关事实误判为有依据，因此必须同时验证错误来源、跨段落引用、混合列表和未知证据编号。修改集中在核验/生成与对应测试，可回退代码，不要求迁移原数据。

可增强简历表述：证据绑定与局部修复、失败恢复，以及引用有效率/任务完成率的实测变化。

## 2. V4：受控的研究—实现—实验闭环

判断：应做，并排在进一步扩大RAG评测与增加检索组件之前。当前V3已有创新假设、实验配置/基线/结果版本及 `research-experiment/v1` 交接合同；缺少的是实际执行与结果驱动的迭代。V4将直接利用这些基础，使项目能够从“给出建议”走到“实现并检验建议”。它也能与已有Coding Agent项目形成明确分工：研究侧负责证据、实验目标和判断，编码侧负责工作区内的修改、测试与日志。

最新实测：精简诊断、明确UTF-8、开发反馈与隔离计分后，第四次Luna运行172.015秒交付通用排序候选，264134累计token；开发Recall@5 90%→80%，测试64.92%→43.89%，not_met。前三次失败完整保留。283项后端、29项前端、V1/V2通过；详见[反馈报告](../evals/reports/v4-first-cycle-20260923/feedback-improvement-20260923/report.md)。

当前优先的小增量是**单轮开发选优**：保存每次开发测量对应的代码快照，以开发Recall/MRR选出不退步的版本；全部退步则保留基线和失败候选，明确输出“未找到改进”。候选锁定后才做一次测试终验，不能用本轮测试退化题继续调参。先用已保存退化案例验证选择/回退，再安排固定预算的一次真实验证；不追加多轮刷正分。该能力尚未实现，不能写入简历为既有成果。

下面两阶段仍是V4总体范围；第一阶段已完成执行/反馈链，第二阶段须等上述质量选择完善后推进：

1. **V4首个闭环：**先接一个本地命令行Coding Agent；用户明确实验工作目录和预算后，读取已锁定的实验合同，在独立实验工作区完成实现、运行既定测试/benchmark，回传真实指标、命令日志、退出码和代码差异，自动与固定baseline比较。首个案例优先选择可在本机短时间执行的检索模块优化，固定数据与指标，使收益和代价都可检查。成功标准是完整运行与正确比较，不要求每个候选都优于基线。
2. **V4有限迭代：**在首个闭环可恢复后，基于验证集结果决定继续修改、完成或停止；加入最大轮次、时长/调用预算、连续无改善停止、取消、恢复和失败回退。只在既定授权范围内继续，不逐步重复询问；实验合同扩大时再处理新增范围。测试集保留作冻结终验，不用它指导每一轮修改。

最小新增能力是执行适配器、实验任务及运行/决策记录；沿用现有实验面板、SQLite、任务生命周期和Trace，不重做资料库、记忆或Coding Agent。将文件和命令权限落实到可验证的执行边界；单纯复制目录或提示词约束不能宣称强沙箱。具体CLI和隔离方式在实施设计时核实支持后选定，本次优先级判断不假定已安装可用。

交付时至少保留一轮成功执行及一轮真实失败/无提升案例；测试基线锁定、指标口径错误、非零退出、超时、取消、预算终止与越界动作拒绝。分别记录实验完成率、测试通过、目标达成、恢复情况、每轮成本/耗时及改动大小。数字必须由后续实际执行产生，首版简历不提前加上V4成果。

工作量与风险高于单个引用修复；主要成本在执行边界、进程生命周期与结果可信性。因此V4内部先交付单轮闭环，再增加有限迭代，不同时开发通用多Agent平台。关闭新执行入口即可退回V3资料/成果工作流；保留新增实验记录，不用旧数据库覆盖新数据。

可增强简历表述：Coding Agent适配、受控工具执行、实验编排、基线比较和预算约束下的反馈迭代。完成一条可展示链路后即可更新简历，无需等待实现所有V4扩展。

## 3. 把策略评测接到实际工作台流程

当前面板支持反馈、候选、评测结果展示和启用/回退，但可信评测主要由独立本地脚本执行；没有从用户候选直接发起评测任务的页面入口。

最小方向：在候选旁提供“运行对照评测”，选择固定用例与模型、显示预计调用上限；由可信后台复用现有任务队列运行基线和候选，将结果写回同一研究区及候选版本。网页只提交用例选择和运行请求，不能提交自报成功率。冻结来源、模型和预算；支持取消、失败保留、结果比较及通过后启用。

交付标准：演示一次反馈→候选→后台评测→结果→通过后启用/未通过保留→回退，整个过程能从界面操作。验证候选归属、取消、模型限制、过期父版本和重复请求；没有合格候选时按实际结果拒绝启用，不伪造通过。

资源边界：沿用已配置模型服务和单机 worker，不新增服务；将评测调用数和耗时纳入预算。复用 V4 的任务展示与结果管理经验，但此入口只运行既有 Harness 固定问答，不继承代码执行权限。

可增强简历表述：真实反馈驱动的策略迭代闭环、版本归因、离线评测门控和回退演示，而不只是脚本层能力。

## 4. 用一次更有代表性的评测替换首版数字

在关键修复、V4闭环和策略评测入口稳定后，把公开语料从6份扩至约20–30份，建立约100–150题，覆盖精确术语、跨文档、来源冲突、无答案、会话记忆和上下文压缩；V4使用另列的实验任务验收，不把两类任务混成一个准确率。数字是下一轮规模建议，尚未完成；题目按来源/主题分离开发与测试，关键事实项对照原文抽查，避免只是批量改写同一问题。各阶段仍有自身的小规模回归/验收，不把必要验证全部推迟到本阶段。

保留当前基线与一到两个明确候选，只安排一轮冻结验收；少量困难题可重复观察波动，成本在运行前固定。先用 Luna；只有存在模型饱和或需要检验跨模型适用性时才引入配置中的 DeepSeek，并记录真实模型标识。

## 5. 按投递方向选择一个强化点

- **偏应用算法：**若新错误分析显示候选已召回但排序不佳，增加一个交叉编码器 reranker 作可关闭的对照，和现有 RRF/确定性覆盖重排比较；若排序已经足够而规划成本高，则优先自适应查询规划，让简单问题走直接检索、复杂问题再展开。先做其中一个，用召回/答案收益与延迟代价共同选型，不预先承诺提升。
- **偏 Agent 开发：**补齐可复现部署与真实任务生命周期演示，重点验证停止、恢复、连续追问、并发提交排队和失败诊断；测实际吞吐、等待时间、恢复成功率，明确单机边界。现有 Docker 配置可复用，不能将未实测的容器/并发能力写成已验证成果。

这一阶段不为技术栈名字替换数据库或引入多 Agent。若目标岗位明确要求工具协议互操作，再增加 MCP 适配；V4已作为前面的独立主线，不再放在岗位专项的可选尾项。

## 每轮结束条件

每轮限定一个主要问题，完成可演示结果、相关回归和约定规模的真实验收，保存 Git 版本、报告、来源与失败，评估是否更新 [简历版本](resume/README.md)。未解决问题进入下一轮，不让当前投递文案等待所有问题消失。

本建议的前提是当前优先提高岗位覆盖和可演示的完整能力，而非只追求问答分数；这与用户的简历项目目标一致。已有失败轨迹支持先短范围修复证据到答案的最后环节，V4随后推进。若用户转向近期上线的高频知识问答场景，再提高服务稳定性、检索规模和延迟优化优先级。
