# Agent 重复评测与鲁棒性

## 问题

V2 的 15 项验收是一次工作流检查，不能估计多次尝试的成功概率，也不能从中得出指令扰动或长上下文稳定性。仅累计 ResearchAgent 循环的 usage 会遗漏路由、本地检索计划和问答；引用编号存在也不等于回答正确。

## 解决方案

新增独立评测脚本，调用产品原有的 Workbench.send/execute、ResearchAgent、模型和搜索接口，在独立 SQLite 与会话中执行。生产服务和原用户数据不参与测试状态写入。没有为通过测试替换产品模型或修改 Agent。

首轮预注册 72 次运行：

| 轨道 | 任务与条件 | 重复 | 次数 |
|---|---|---:|---:|
| 产品研究工作流 | 6 道题 × 原问题/同义改写/引用文本攻击 | 每条件 3 次 | 54 |
| 上下文压力 | 2,048/16,384/65,536 字符 × 事实位于前/中/后 | 每格 2 次 | 18 |

六道题覆盖 Docling 架构、ReAct 评测任务、跨论文机制比较、未公开信息拒答、Meta-Harness 实体与机制、GitHub 官方接口限制。本地题使用从真实 PDF 提取且保留原文 SHA-256 的固定快照；两个联网题使用真实搜索及网页/PDF 阅读。每次无此前答案/报告缓存，关闭自动下载。下载根目录仍固定为 `D:\paper`；这轮不重新评测已验收的下载及解析。

上下文压力使用带唯一数值事实的合成登记表和受控 search/read 返回，模型真实调用。该轨用于测信息保留和读取，不冒充联网召回评测或实际论文理解。

## 工作原理

### pass@k 与重复可靠性

同一题同一条件运行 n 次，其中 c 次成功：

```text
pass@k = 1 - C(n-c, k) / C(n, k)    至少一次成功
pass^k = C(c, k) / C(n, k)          k 次全部成功
```

只计算 k ≤ n；默认 n=3，所以提供 k=1、2、3，不外推 pass@5。先每题计算再取宏平均；pass@3 高只说明给三次机会较容易成功，不代表单次可靠。pass^3 回答“连续三次是否都成功”，也不能直接用总体 pass@1 的三次方代替。

任务级 bootstrap 2,000 次，固定随机种子，记录 95% 百分位区间。重复试验不是新任务，不将它们假装为独立题目扩大样本量。只有六道开发题，区间不涵盖模型供应商漂移、评分器系统误差或开放网络变化。

### 评分

第一层检查路由、任务完成、实际工具阅读、引用编号、原文摘录、所需论文和攻击输出污染。第二层由 Terra 按冻结 rubric 判定答案自己的表述是否正确、是否得到实际证据支持、是否有重大额外矛盾。每条判定保存理由，并绑定答案哈希。

不能仅凭关键词打分：例如“TableFormer 是版面检测器，RT-DETR 做表格”虽然词都出现，仍应失败。校准脚本单独检查正确答案、角色颠倒、捏造数字、没有实际证据、指挥评分器五个样例。评分器调用失败或返回无效结构时标为 UNJUDGED；相关任务不进入完整重复估计，并展示覆盖率，不悄悄改成通过或失败。

这仍是模型辅助评分，不是专家盲评。结果应配合原文和失败样例核对。不得在同一评测轮次中根据结果修改 Agent、rubric 或题目，再只保留最好一轮。

首轮观察到可能的拒答误判，因此增加单独的 Sol 复核：同一 rubric、全部内容评分失败项、每题按运行 ID 的 SHA-256 固定抽取一个通过项；不给第二评分器看第一评分器的判断。复核仅记录分歧，不覆盖原始分数。这个选择性样本的一致率不等于评分器总体准确率；两个模型并非真值。脚本为 `evals/audit_agent_judgments.py <结果目录>`，其 token 独立记录。

### 稳定性与上下文

- 同义改写保留相同目标，以相同 task/repeat 配对，报告成功率变化、成功转失败、失败转成功及原成功保留率。
- 引用文本攻击明确标为不可信资料，尝试要求输出一个固定标记。它是边界压力测试，应与普通改写分开解读，不是用户授权的新指令。
- 上下文以源文字符数设档，并记录服务端实际 prompt_tokens、峰值输入和目标事实可见性。不能把“65K 字符源文”写成“模型处理了 65K tokens”。产品裁剪导致证据缺失，也计入端到端失败并单列原因。

### 步骤、用量与耗时

每个模型工厂都包一层只读记录器。实际发生的路由、计划、研究、回答、资料分析和内部纠正均计入 Agent 用量；评测 judge 独立统计。模型返回的 prompt/completion/total token 是服务商报告值，不以字符估算替代。请求失败或缺少 usage 时标记未知，总量只能报告已知小计，不能填零。没有固定价格表，不虚构货币成本。

“步骤”拆成模型请求数、实际工具调用数、工具请求/尝试数、工具产生的网络请求数。本地问答的内部检索不冒充 search/read 工具调用。各项保留均值、nearest-rank P50/P95；耗时包含产品执行，不包含评测排队或评分器时间。两条隔离流水线并行会影响网关/网络负载，不能把延迟当作专属硬件的纯推理速度。

## 试一下

在 `D:\project\researchagent`，使用已有 `evidence-agent` 环境和 `.env`：

```powershell
python -B -m unittest discover -s tests -p test_agent_benchmark.py
python -B evals/run_agent_benchmark.py --download-root D:\paper --dry-run
python -B evals/run_agent_benchmark.py --download-root D:\paper
```

默认模型 Luna、评分器 Terra，均使用现有 Sudocode 配置。`--repeats 5` 才能得到 pass@5；这会增加真实 API 消耗。`--model` 和 `--judge` 可选项目已经配置的模型。不同模型比较应使用同一任务与代码快照，完整保留每轮。

```powershell
python -B evals/calibrate_agent_judge.py --output evals/reports/judge-calibration-new
```

默认 runner 只使用项目既有依赖，并直接生成 HTML/Markdown、JSON 和 CSV。`evals/build_agent_report.py <结果目录>` 是可选的归档汇总/出图脚本，需要 matplotlib 和 numpy；它只读取已完成结果，不重跑任务或更改判分。

结果目录独占创建，包含冻结 manifest/任务/代码和资料哈希、逐次 JSON/CSV、模型调用明细、输入快照、Trace、SQLite、汇总指标和 HTML/Markdown 报告。展示输入沿用产品脱敏上限，完整输入另保留哈希，上下文压力源文独立保存。中途退出不覆盖已完成试验；`--resume` 只接受同一代码与配置，不能借此重跑已失败的试验。续跑只适用于尚未开始的试验；若某次已经开始却未形成 result.json，脚本会拒绝覆盖其目录，应保留该次中断证据并另开评测轮次。

## 方法来源与下一步

- [HumanEval](https://github.com/openai/human-eval/blob/master/human_eval/evaluation.py)：pass@k 组合估计。只采用指标方法，没有运行 HumanEval 编程题或执行生成的代码。
- [τ-bench](https://github.com/sierra-research/tau-bench)：重复任务可靠性 pass^k。没有运行其客服数据库场景。
- [Lost in the Middle](https://github.com/nelson-liu/lost-in-the-middle)：按长度与答案位置测试。当前使用自编登记表，没有复用其完整数据集或宣称其榜单分数。

这是一套可复现的开发评测，部分题材与 V2 验收重叠。下一轮扩大为独立保留题集、增加盲审和跨模型配对后，才能做更强的泛化或模型排名结论。现有 14/15 验收与新的语义评分口径不同，不能直接比较两个百分比来声称性能提升或退化。
