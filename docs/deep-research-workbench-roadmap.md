# 深度研究工作台实现路线



创建日期：2026-09-14。执行项目：`D:\project\researchagent`。



路线更新（2026-09-21）：V1 已实现，工程验收和真实联调边界见 [V1 验收记录](v1-validation.md)。V2 已部署并完成真实模型/浏览器测试，自编任务 14/15 通过，剩余引用失败及完整指标见 [V2 验收](v2-validation.md)；V3 已实现并完成本轮工程与真实案例验收，当前能力与边界见 [V3 研究成果](v3-research-records.md)；V4–V5 仍为后续计划。



## 目标



将当前“证据驱动 Research Agent Harness”演进为面向计算机专业研究生的深度研究工作台：用户可以创建研究区，在研究区内进行普通聊天、发起模糊或明确的研究任务、沉淀论文和技术资料、生成可追溯报告，并在后续阶段与本地 Coding Agent 配合完成“研究—实现—实验—迭代”闭环。



最终主链路：



```text

研究区 → 对话/意图识别 → 后台研究任务 → 论文/文档/GitHub 调研

       → Evidence/Claim → 报告与资料归档 → 创新方案

       → Coding Agent 实现 → 实验指标 → 与 Baseline 对比 → 迭代

```



## 设计边界



- 继续复用当前 `ResearchAgent`、Evidence、Claim、Policy、Trace 和 SQLite 基础。

- 核心编排仍使用普通 Python 显式流程，不引入 LangGraph 作为黑盒运行时。

- 先完成单用户、单机、可恢复的工作台，再考虑多用户和分布式任务队列。

- 论文下载、命令执行、工作区写入都属于有副作用的动作，必须有路径校验、权限边界和用户可见记录。

- 普通聊天不强制搜索；只有识别为研究任务时才进入检索流程。

- 自动生成的创新点是候选方案，不得直接当成事实或自动修改代码。

- 每阶段同步中文教学文档（问题、解决方案、工作原理、试一下、接下来），完成真实样例、失败样例和相应评测后再验收。实现前核实相关 2024–2026 年论文及优秀开源实现，使用 think 确认设计、ponytail 检查复杂度；引用必须区分正式发表与预印本。

- 评测与 CI 从 V1 开始建设；V5 做综合验收，不把质量验证推迟到最后。



## 分阶段实现顺序



### V1：研究区、对话和后台任务



目标：从“一次请求对应一次 Run”升级为可持续使用的研究区。



功能：



1. 研究区 CRUD：名称、描述、下载根目录、创建时间、更新时间。

2. 研究区内的 conversation 和 message 历史。

3. Intent Router：至少区分 `CHAT`、`RESEARCH`、`LOCAL_QA`、`DOWNLOAD`、`BRAINSTORM`、`EXPERIMENT`。

   使用 LLM 结合会话历史输出结构化意图，由服务端校验并路由。V1 执行聊天与研究；后续阶段的意图只说明尚未支持，不能伪造工具执行结果。

4. 模糊研究意图澄清：例如“我对 Agent 有兴趣”转成研究方向探索任务，而不是直接回答一句定义。

5. 后台任务状态：`queued`、`running`、`completed`、`failed`、`cancelled`。

6. 前端显示任务进度、当前阶段、最近动作和最终摘要。

7. 研究报告以 Markdown/HTML 文件和数据库元数据两种形式保存。



数据表建议：`research_spaces`、`conversations`、`messages`、`research_jobs`、`reports`。



验收：



- 可以创建两个独立研究区，历史记录互不混淆。

- 输入“你好”只走聊天路径，不调用搜索。

- 输入“我想研究一下 Agent”会创建后台研究任务并返回 task ID。

- 刷新页面或重启服务后，任务状态和历史仍可查询。

- 前端断开不终止后台任务；进程重启后将未完成任务标为 interrupted，用户可重试，不能一直显示 running。数据库变更需迁移已有 runs，不能删除旧数据重建。



### V2：论文、技术文档和 GitHub 资料工作流



目标：让 Agent 能够真正处理研究资料，而不是只回答搜索摘要。



功能：



1. 论文识别、元数据抽取和 PDF 下载。

   按经典、代表性、最新研究分别选择资料，并记录入选理由、发表年份、会场/期刊及预印本状态。优先一手来源，避免用 GitHub star 数代替研究质量。

2. 用户配置下载根目录；所有路径必须限制在用户授权目录内。

3. 自动目录：`研究区/主题/论文/年份-标题/原文.pdf`、`报告.md`、`metadata.json`。

4. PDF 文本抽取和章节切分，优先识别 abstract、introduction、method、experiment、result、limitation。

5. 论文结构化分析：研究动机、问题定义、设计思路、方法实现、实验设计、结果、局限性。

6. 技术文档和 GitHub 默认只阅读和分析；只有用户明确要求时才下载或克隆。

7. GitHub 项目分析：README、目录树、关键模块、依赖、入口、测试和运行方式。

8. 本地资料索引：按研究区管理论文、报告和允许读取的文档。

9. 本地问答必须绑定本地 Evidence，并显示文件路径和章节位置。



下载策略：在研究区设定目录和预算后自动下载可获取的论文 PDF；付费、访问失败或非 PDF 内容需说明，不能声称已通读。按 DOI/arXiv ID 和文件摘要去重，采用临时文件完成后再重命名，避免同名覆盖与半文件。表格、公式或扫描页解析失败应保留页码并标注理解边界。



这里的“本地路径”指后端所在计算机的目录；本机运行时可指定 Windows 路径，Docker 运行时须挂载对应目录。远程浏览器不能直接指定其自身硬盘作为服务器写入位置。



数据表建议：`artifacts`、`papers`、`documents`、`document_chunks`、`citations`。



验收：



- 给定论文 URL 可以下载到用户指定目录，重复下载不会破坏已有文件。

- 论文报告能区分“论文原文事实”和 Agent 推断。

- 用户询问本地论文时，不访问未授权路径，不把其他研究区资料混入答案。



### V3：研究报告、创新方案和研究记忆



目标：让研究结果可持续积累，并能支持下一轮研究决策。



功能：



1. 报告版本管理：草稿、审核版、发布版。

2. Claim-Evidence 图：每个主要结论显示证据、来源类型、时间和验证状态。

3. 研究主题图谱：论文、项目、方法、数据集、指标和结论之间的关系。

4. 基于已有资料生成创新候选：问题缺口、核心假设、方法变化、预期收益、风险和验证实验。

5. 创新点必须引用已有研究依据，并明确标记为 `HYPOTHESIS`，不能伪装成已验证事实。

6. Baseline、目标指标、实验配置和结果版本化。

7. 研究区级摘要记忆：只保存已验证事实和用户确认的研究偏好。



数据表建议：`ideas`、`baselines`、`experiments`、`metrics`、`memory_items`。



验收：



- Agent 能从至少两篇已有论文生成带依据的创新候选。

- 每个创新候选能追溯到具体论文、Claim 和 Evidence。

- 用户可以比较不同方案和不同实验版本。



### V4：与 Coding Agent 的实验闭环



目标：实现“研究 Agent 提方案，Coding Agent 写代码并跑实验，研究 Agent 评估结果”的受控闭环。



功能：



1. 定义本地 Agent Adapter 协议，先支持命令行适配器，再接入 Codex/Claude Code 等具体工具。

2. 研究 Agent 输出结构化实现任务：目标、输入、文件范围、验收指标、禁止操作。

3. Coding Agent 在隔离 workspace 中实现，所有高风险命令和文件变更可审计。

4. 运行测试、benchmark 和实验脚本，采集结构化指标。

5. 自动与 Baseline 比较，判断达到目标、部分达到、失败或需要重新设计。

6. 支持最大迭代次数、预算和用户终止。

7. 用户一次设定目标、工作区及资源预算并授权后，研究 Agent 根据实验反馈自动迭代；仅在需要扩大范围、超出预算或执行未授权高风险动作时请求确认。



实验合同必须固定数据集版本、训练/验证/测试划分、baseline 代码版本、执行命令、随机种子、指标方向和目标（绝对百分点或相对提升）。开发迭代使用验证集，最终用冻结测试集验收；不得更换口径或反复调参到测试集来制造达标。达到目标、预算耗尽、用户取消或连续无改进都应给出可追溯的停止结果，不能保证任意创新目标一定达成。



数据表建议：`agent_runs`、`workspace_snapshots`、`experiment_runs`、`metric_observations`、`iteration_decisions`。



验收：



- 一个简单可复现的 benchmark 能完成至少一轮“方案—实现—运行—比较”。

- 指标、日志、代码变更和研究报告之间可以互相追溯。

- Coding Agent 无法越过授权目录和命令策略。



### V5：质量、评测和产品化



目标：让项目从个人可用工具变成可信的简历级工程项目。



功能：



1. 按意图、研究类型、资料类型和失败原因扩展评测集。

2. 分别评估聊天正确性、研究任务完成率、Claim 支持率、下载成功率、本地问答准确率、创新方案可验证性和实验闭环成功率。

3. 统计 Pass@1、Pass@k、Pass^k、P50/P95 延迟、token/cost、任务恢复率和安全拦截率。

4. 至少对比普通单轮搜索、无反馈多跳和证据反馈三种配置。

5. 增加 CI、数据库迁移检查、Docker smoke test 和数据脱敏检查。

6. 前端显示失败原因和可恢复操作，而不是只显示“请求失败”。

## 不在第一阶段实现的内容



- 多用户账号、云端同步和分布式队列。

- 向量数据库和复杂检索编排；先用 SQLite + 可替换的本地索引接口验证需求。

- 第一阶段不修改用户代码或发布论文。后续论文自动下载和实验自动迭代按用户已授权的目录、范围及预算执行，无需每步重复确认。

- 直接把模型生成的创新点当作研究结论。

- 训练专用模型或 Agent-RL；该方向留在 `D:\project\newagent` 的 Harness 项目中。
